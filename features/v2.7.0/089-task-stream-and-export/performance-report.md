## 流式与页面

| 项目 | 实测 | 测量边界 |
|---|---|---|
| 用户提供的双后台调研会话 | 后期正文转发积压最大 53781ms | 同一 worker 的 monotonic，收到文本至持久事件写入；不是模型推理时间 |
| 改为异步历史投影后的独立双成员任务 | 28 帧，P50 265ms，P95 281ms，最大 296ms | 同一时钟；不含网络和浏览器绘制；该次任务非固定压测 |
| 浏览器真实增量 | 同一成员正文 546 → 2804 字；状态“正在执行 · 15s”→“已完成 · 25s” | 正文完成前已显示；两成员分别归属不同 invocation_id |
| 长历史 | 10000 事件、2000000 文本字节、20 个片段；5 次投影与建树 4.76–7.44ms | 实际 TypeScript reducer 在 Node 执行，**不含浏览器绘制/滚动** |
| 节点容量 | 12 个并发请求，最多同时执行 2 个，6 个完成、6 个明确拒绝；结束后两个租约集合均为 0 | Windows 访问远端 Redis，专用随机 node id，不向共享任务队列压测 |
| 慢存储 | SQL 写入被人为阻塞时，100 个后续片段仍能更新投影；不可变旧快照不被追加污染 | 自动测试，有最终 flush 和错误传播；内存中无逐 token 持久化队列 |

前端批量提交窗口 100ms，后端文本合并窗口 250ms、8192 字符、16 帧；语义边界立即刷新。计时 tick 仅刷新状态文字，不反复解析长 Markdown。最终成员正文与委派结果相同时只保留一份 DOM 正文。

回答前的停顿应分开看：本次证实存在系统历史写入积压；此外模型首字/推理、工具实际执行和 job_output 等待仍可能耗时。本次没有测得每次请求的供应商 TTFT，不能把所有空白归因于模型或沙箱，也没有通过模拟打字掩盖上游等待。

## 双平台真实报告样例

同一固定输入：10 个章节、2 张嵌入图片、5 张表、多页中英文与编号列表。以下为进程创建、转换与核验完成的本机耗时；已排除远端文件下载。

| 环境/引擎 | DOCX | PDF | HTML | 缓存命中 |
|---|---:|---:|---:|---:|
| Windows 原生 / LibreOffice | 0.588s | 5.609s（12 页） | 0.371s | 20–24ms |
| Linux Docker / LibreOffice | 0.977s | 5.455s（9 页） | 0.367s | 16–23ms |
| Windows / Chromium（现有 Edge） | 0.713s | 3.041s（11 页） | 0.482s | 23–25ms |
| Linux Docker / Chromium | 约 0.79s | 2.133s（11 页） | 约 0.36s | 13–15ms |

Windows 为 Python 3.11.14 / Windows 10.0.26100；Linux 为后端现有镜像、Python 3.11.15 / WSL2 Linux 6.6。字体分别为 Microsoft YaHei、fontconfig CJK。Chromium 两组为表格禁止拆行补丁之前的同结构实测；LO 两组为该补丁之后。页数因平台字体替换不同，未声称跨平台像素相同。

两平台另行运行了隔离核验进程，DOCX 均检出 2 图/5 表，PDF 可逐页解析，HTML 内嵌资源可核验。Windows 经真实远端容量租约执行；Docker 到远端 Redis 的网络连接超时，Linux 的纯解析进程复测只在验证脚本中使用空容量上下文，**不能视作 Linux 远端中间件集成通过**。生产没有禁用容量控制；Redis 协调操作增加 5 秒超时与有界租约回收。

## 未关闭的预算

真实模型追加验证见 [real-task-validation.md](./real-task-validation.md)：同题短答正文首字15.657→8.758秒、总耗时20.578→11.602秒；技能Word/Excel任务最终68.859秒，9次主模型调用。协作总耗时未改善，原成员残留测试提示仍增加调用；另有一次223.120秒的失败性能复测已保留。小样本、不同并行条件不可当成稳定P95；首字前仍包含约6秒平台准备，不能全部算作模型延迟。

- 实际信创浏览器、禁 GPU/4 倍 CPU 节流后的滚动与输入 P95。
- 20 次会话切换、强制 GC 后 retained heap、完整后代进程峰值 RSS。
- 固定 3 成员 × 30 增量/秒 × 2 分钟、并发转换时的完整聊天/API 对照压测。
- 浏览器 WS 接收到 paint 的精确 P95，以及全矩阵严格前后对照。

这些是未验收项，不以单元测试或主观流畅代替。输入/图片/ZIP 展开、并发、队列、缓存、子进程超时已有明确边界；512MiB 临时工作集仍是待测目标，当前没有强制 RSS 限制。

原始本机证据保存在 `src/backend/.venv/f089-evidence/`，包括 latency、capacity、projection、benchmark 与双平台 validation JSON；该目录被忽略，不提交原始用户事件或带签名链接的日志。

报告核验跟进：用户新会话出现缺少 pdftoppm 后安装 Poppler，并重复全量渲染 18/17 页。提示改为优先已有 PyMuPDF、首轮最多 3 页、80–96 DPI，发现问题再扩查；这是行为指引，尚未以新真实模型任务证明其耗时收益。列表修复的单页真实 LibreOffice 样例：Windows 5.029s、Linux 1.730s（含本地转换及输出），图片各 1 张、页数各 1；此小样例不能与前述 10 章节预算直接比较。
