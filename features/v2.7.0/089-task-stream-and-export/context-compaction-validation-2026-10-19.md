# 单会话超过 200K 的真实压缩验收

日期：2026-10-19。结论：**自动压缩及关键信息保留通过；200K 不是硬性请求上限，长历史状态重建仍有性能问题**。范围：用户要求在默认压缩阈值调整为 200,000 tokens 后，用一个 session 实际累积超过 200K 上下文并验证压缩。使用真实模型、远端 Redis 与 MinIO；不降低测试阈值、不向检查点注入伪历史、不使用累计输入量冒充当前上下文。

## 触发阈值的含义

200K 是调用前检查的压缩触发阈值，**不是任何请求或压缩结果的硬性 token 上限**。SDK 结合估算和已有模型用量判断，当前调用可能越过阈值，在后续调用前触发压缩；流式生成中不会在第 200,000 个 token 强行截断。

默认保留最近 6 条消息。该测试刻意使单条消息很大，因此前三次压缩后实际输入仍约 263K；被保留的近期消息本身就很大。继续推进保留窗口后，本次实际输入降到 181,026。不能据“已压缩”声称所有请求始终小于 200K；若产品需要严格请求预算，还需要另行设计按 token 约束的近期保留策略。

## 本轮发现并修复的问题

浏览器实测发现压缩器内部摘要调用的文本/思考混入了用户执行记录。SDK 为这些调用提供 `lc_source=summarization` 元数据，原事件映射没有过滤它。

已在 `StreamEventMapper.normalize` 入口过滤该类内部消息，避免改变正常思考段身份、正文内容或工具事件，也不影响压缩和检查点持久化。新增回归覆盖“内部摘要不展示、正常思考不被切断、正常正文仍展示”；压缩边界、真实 SDK 装配、流映射与交付筛选相关 **76 项通过**。Ruff、架构守卫及差异检查通过。Worker 在确认空闲后重启，继续使用原测试会话复测；此前已持久化的旧执行记录没有被改写。

同会话修复后两轮约 196 秒、187 秒；再次产生摘要，新增执行事件 2 条，内部摘要混入 0 条，三个标签仍全部正确。

另发现框架的 `conversation_history/` 归档被旧的“本轮新文件”兜底规则当作报告交付，已将该目录与 `large_tool_results/` 纳入内部非交付区。使用刚从 MinIO 读回的 452,057 字节归档，在真实文件扫描与筛选链路验证归档被排除，同时 `output/history-summary.md` 正常保留。该修复做了单元回归与真实归档集成验证，没有为验证它再发送大模型请求；旧测试轮次的历史附件不追改。

最终 Worker 已空闲重启加载全部修复，心跳有效、私有队列为空、API health 200。显示复测结果及截图在下述证据目录保留。

## 性能观察及剩余问题

同一会话前 8 轮从接续请求到终态约为 9、32、50、71、99、121、142、149 秒；第 8 轮显示复测约 **196 秒**。性能随持久历史增长明显变差，压缩没有消除状态重建的开销。

该轮日志中，Worker 于 16:31:47 开始接续，首个模型 POST 于 16:34:38 发出，正常模型回答于 16:34:55 完成；主要等待发生在模型请求之前，不能归因为模型长时间生成。当前 Redis checkpointer 重建时会读取历史检查点，并通过 SCAN 查找 pending writes 后逐条 HGETALL，是需要专项剖析和优化的候选路径。本轮没有修改检查点存储协议，不能声称该性能问题已修复。

辅助取证最初直接读取最新检查点的 channel_values，误将增量记录看成空历史，已改用 LangGraph `aget_state` 重建，并与真实模型 usage、API 回答及 MinIO 原文交叉核对。原始辅助脚本中的“压缩后必须低于 200K”断言也不符合当前保留 6 条消息的契约；最终结论没有将这些辅助脚本断言当作产品故障。
