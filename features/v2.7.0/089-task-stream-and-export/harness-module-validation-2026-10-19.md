## 性能及体验观察

R1 从真实浏览器提交到最后持久事件约 **106.712 秒**，首次持久化思考事件 **11.408 秒**、首次正文事件 **27.987 秒**、首次代码工具调用 **30.960 秒**。这些使用提交时刻和 Redis event ID 计算，包含调度及持久化，不是浏览器绘制时延，也不能当作纯模型 TTFT。首次正文可能来自主 Agent 或成员，未将两者混称为主 Agent 首字。

本例首次代码调用发生在首次思考事件之后，因此不能把开头等待归因于代码沙箱调用。缺少提供商首 token、排队、图初始化和持久化分段 span，尚不能准确分摊这 11.4 秒。多模型调用、先规划再委派与工具往返都会增加总时长。

综合任务两个成员约 41 秒和 25 秒，存在并行执行；主 Agent 11 次、成员合计 9 次模型调用，累计输入约 191K tokens。主 Agent 已有两名独立核算成员，随后又调用代码复算，增加调用和上下文成本。该任务产出约 3.9KB Markdown，超过用户设定的简短报告目标，说明最终精简约束仍有改进空间。不能据单次任务推出吞吐、P95 或生产并发能力。

浏览器 CDP 留存存在截断，未用它声称所有帧延迟均已精确测量；完整顺序/去重结论以真实 WebSocket 断连重连断言为依据。时钟和流式组件另有定向自动回归。待办更新仍取决于模型实际调用 write_todos；流传输正常不等于模型会及时更新待办。
