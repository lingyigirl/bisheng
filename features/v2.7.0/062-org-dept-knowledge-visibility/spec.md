# Feature: 机构/部门标记与树形知识库可见范围（062-org-dept-knowledge-visibility）

> **本文档定位 — 纯 What（需求口径，不随代码漂移）**
>
> spec 只回答 **做什么 / 验收标准 / 不做什么**。
> **所有 How（决策、数据流、字段、API、Service、前端、文件清单、性能指标）一律不写在这里。**
> How 的唯一真相在 [design.md](./design.md)（接手必读）与 [tasks.md](./tasks.md)（执行流水）。

**关联 PRD**: 用户需求（2026-09-21）：机构/部门树上需要区分「机构」与「部门」两类节点，并据此确定树上知识库的默认可见范围——「叶子节点能使用到根节点上的知识库，以及树枝节点/根部和树枝节点/根部下其他部门的知识库」。当前 F057 只实现了「归属部门向下传递」（纵向），横向的同级/叔伯部门之间不可见，无法表达「同一个机构内部互通」这一实际组织语义。
**优先级**: P0
**所属版本**: v2.7.0
**依赖**: F057-knowledge-department-ownership（部门归属与读时求值的可见性口径）；部门树模块（既有）、知识库权限体系（既有）。不新增错误码（拒绝路径复用既有 HTTP 403 信封，与 F057 同口径）。

> **范围边界**（写清「明确不做什么」比写「做什么」更能防 scope 膨胀）
> - **本次纳入**：
>   - **机构/部门标记**：部门树节点上新增一个二值标记（机构 / 部门），区分组织层级语义
>   - **标记的配置入口**：在组织管理页可为单个节点设置标记，并支持批量设置
>   - **初始化引导**：存量组织树在被标注前，提供引导提示与批量标注入口
>   - **默认可见范围规则**：树上知识库按「机构域」确定可见范围，含纵向链路与机构域内的横向部门
>   - **变更保护**：标记翻转与移动节点属大范围权限变更，需影响面提示、确认与留痕
>   - **一致性口径**：全部知识库读取入口（客户端列表 / 平台列表 / 部门数量角标 / 工作台对话检索 / 灵思任务内核）使用同一份可见集合
> - **本次明确排除**：
>   - **知识空间（`knowledge_space`）的部门穿透**：知识空间沿用其既有的成员制可见性口径，不适用本规则（本期只作用于组织知识库，与客户端实际过滤面一致）
>   - **知识库级 / 部门级的可见性排除**：本期不提供「某个库不开放给某部门」这类例外机制；需要隔离时通过调整树结构（标注机构、移动节点）表达。理由见 INV-20
>   - **标记的继承**：新建节点不从父节点继承标记，必须显式选择
>   - **根节点类型的约束**：根节点标为机构或部门均可，规则对其无差别（见 AC-14）
>   - **`department` 表以外的组织层级**（如用户组、角色）参与本规则
>   - **可见性集合的物化 / 去规范化缓存列**：本期按读时求值，不做预计算列
>   - **撤销隐含授予**：见 INV-20，平台不提供该能力

## 1. 用户故事

作为 **组织架构管理员**，
我希望 **把组织树上的节点区分为「机构」与「部门」，并让知识库的可见范围跟着这个区分自动确定**，
以便 **不用为每个知识库、每个部门手工维护一堆授权，组织调整时可见范围自动跟着走**。

作为 **银行分支机构的员工**，
我希望 **能看到本机构本部及本机构下各部门的知识库，同时也能看到上级机构各条线下与知识库相关的部门知识库，但看不到其他平行机构的内容**，
以便 **在机构内部协作畅通的同时，机构之间保持应有的信息隔离**。

作为 **系统管理员**，
我希望 **在把某个节点从「机构」改成「部门」（或反向）之前，先看到这个动作会让多少个部门、多少个知识库的可见范围发生变化**，
以便 **避免一次误操作静默地把一批合规文档开放给不该看到的人**。

## 2. 验收标准

### 2.1 机构/部门标记与配置

- **AC-01** — THE SYSTEM SHALL 为组织树的每个节点维护一个二值标记，取值为「机构」或「部门」。
- **AC-02** — WHEN 系统升级到本版本, THE SYSTEM SHALL 把既有全部节点一律置为「机构」，且**任何用户对任何知识库的可见范围与升级前逐条相同**。
- **AC-03** — WHEN 创建节点, THE SYSTEM SHALL 不继承父节点的标记，默认置为「机构」，并允许创建者显式选择「部门」。
- **AC-04** — IF 操作者不是系统管理员或租户管理员, THEN THE SYSTEM SHALL 拒绝其修改节点的机构/部门标记（返回 403），**同时**不得影响该操作者对本节点其余字段（名称、排序、默认角色等）在其管辖子树内的既有编辑能力。
- **AC-04a** — THE SYSTEM SHALL 使系统管理员可修改租户内任意节点的机构/部门标记；使**租户管理员**可修改的范围与其既有的部门管理范围一致（即限于其管辖子树内），**不得**因本特性而扩大或缩小该范围。
- **AC-05** — WHEN 操作者提交标记翻转（含**批量**设置标记）或节点移动, THE SYSTEM SHALL 在提交前展示受影响的范围数量（部门数量与知识库数量），并要求确认后才执行。
- **AC-06** — WHEN 标记翻转（含批量）或节点移动被确认执行, THE SYSTEM SHALL 使新的可见范围**立即生效**，不得存在「已翻转但部分用户仍可见」的时间窗口。
- **AC-07** — WHEN 标记翻转（含批量）或节点移动执行, THE SYSTEM SHALL 记录审计信息（操作者、节点、变更前后取值、影响范围数量）。
- **AC-08** — WHERE 当前租户的组织树中不存在任何标记为「部门」的节点, THE SYSTEM SHALL 在组织管理页展示可关闭的提示，引导操作者进行标注，并提供多选后批量设置标记的入口。
- **AC-08a** — THE SYSTEM SHALL 在组织管理页明确呈现每个节点的「机构 / 部门」标记，使操作者可直接分辨当前的组织层级划分与下一步需要标注的节点。

### 2.2 可见范围规则

> 规则口径（需求原文的精确化）：某知识库归属部门为 D，用户所属部门之一为 U。
> **D 对 U 可见，当且仅当「D 自身或其最近的机构祖先」是「U 自身或其祖先」。**
>
> 等价的判定式：记 `N` 为 D 自身（D 是机构时）或其**最近的机构祖先**，
> 则 `D 对 U 可见 ⟺ N 的物化路径是 U 的物化路径的前缀`（含 N == U）。
>
> **该判定式是本节的唯一口径，`2.2` 各条只是它在不同树形上的表现，不得各自另立解释。**

- **AC-09** — WHEN 知识库归属部门为 D, THE SYSTEM SHALL 对该知识库应用本节的可见范围规则，D 的上级方向按「最近的机构祖先」截断。
- **AC-10** — WHEN D 位于 U 的祖先链上（U → 其上级 → … → D，链路中间无机构）, THE SYSTEM SHALL 对 U 的用户授予该知识库的可见性（纵向链路）。
- **AC-11** — WHEN D 与 U 同处一个「机构域」（即 D 与 U 的最近公共祖先是**机构**，且从该公共祖先到 D 的路径上**除该公共祖先自身外**不含其他机构）, THE SYSTEM SHALL 对 U 的用户授予该知识库的可见性（机构域内横向互通）。
- **AC-11a** — THE SYSTEM SHALL 按上述口径把「公共祖先自身是机构」视为**不阻断**：D 与 U 的最近公共祖先为机构时，二者仍属同一机构域。该条与 AC-14 共同约束——根节点标注为「机构」时，根下各条线的部门之间必须互相可见。
- **AC-12** — IF D **是** U 所在机构域之下的嵌套机构, THEN THE SYSTEM SHALL 不授予该知识库的可见性（嵌套机构节点本身构成边界）。
- **AC-12a** — IF D 位于 U 所在机构域之下的嵌套机构**之内或之下**（含该嵌套机构的直属部门及其任意层下级）, THEN THE SYSTEM SHALL 不授予该知识库的可见性。
- **AC-13** — THE SYSTEM SHALL 在机构域内部不受中间部门层级的数量限制（部门可作为纯粹的层级节点，可穿透任意多层）。
- **AC-14** — THE SYSTEM SHALL 使根节点标注为「机构」或「部门」对该用户的可见范围**不产生任何差异**。
- **AC-15** — WHEN 用户同属多个部门, THE SYSTEM SHALL 取各所属部门可见范围的**并集**。
- **AC-16** — IF 用户不属于任何部门, THEN THE SYSTEM SHALL 该用户不因本规则获得任何知识库的可见性。
- **AC-17** — THE SYSTEM SHALL 对因本规则可见的知识库只授予**查看与使用**权限，**不授予**编辑、删除、成员管理、所有者管理等权限。
- **AC-18** — THE SYSTEM SHALL 不把本规则应用于知识空间与个人知识库；二者沿用各自既有的可见性口径。
- **AC-19** — WHERE 多租户开启, THE SYSTEM SHALL 可见范围判定限定在当前租户的组织树与知识库内，不跨租户生效。
- **AC-20** — WHEN 租户内全部节点均标记为「机构」, THE SYSTEM SHALL 可见范围退化为「归属部门及其各级下级部门」（即 F057 的既有口径），不产生任何横向可见性。
- **AC-20a** — IF 机构节点被**归档或删除**, THEN THE SYSTEM SHALL 该节点与其名下知识库一并退出可见范围，**不得**因此使任何用户看到归档前不可见的知识库（隔离边界随机构失效而**收紧**，不失效为「不再隔离」）。
- **AC-20b** — IF 机构节点被归档或删除, THEN THE SYSTEM SHALL 其子树内的用户失去经由该机构获得的横向可见性，**仅保留**其自身归属链上其余未归档机构所派生的可见性。

### 2.3 跨入口一致性

- **AC-21** — THE SYSTEM SHALL 对客户端组织知识库列表与平台知识库列表使用**同一份**可见集合；同一个知识库不得出现「某入口可见、另一入口不可见」。
- **AC-22** — THE SYSTEM SHALL 使平台部门树上每个节点展示的知识库数量，与点击该节点后列表实际返回的条数相等。
  > 平台部门树的筛选是**子树收窄**（F057 AC-09），与角标的子树汇总口径同向；二者共用同一份逐库权限判定，因此本特性改变判定后**两者自动保持一致**。本条**不需要改动既有实现**，但必须纳入回归——它是可能被本特性弄坏的既有不变量。
- **AC-23** — WHEN 用户通过对话检索使用知识库, THE SYSTEM SHALL 应用与列表相同的可见范围判定；不得出现「列表不可见但可被检索命中」或「列表可见但检索被拒」。
- **AC-24** — THE SYSTEM SHALL 对**工作台对话**与**灵思任务内核**使用与列表相同的可见范围判定；二者均不得出现「列表不可见但可被该入口检索命中」。本条为 AC-21 / AC-23 在各入口上的逐一落实，凡新增知识库读取路径一律适用。
- **AC-25** — WHEN 本特性引入机构域口径, THE SYSTEM SHALL 使 F057 已发布的验收标准 AC-03a / AC-03b 改用本 spec §2.2 的机构域定义（**单一口径，两处不得各自解释**）；F057 的 AC-03、AC-05 的对外语义不变。

## 3. 边界情况

- 组织树为空 / 用户不属于任何部门 → 不产生任何本规则派生的可见性，全部退回既有 ReBAC 口径。
- 知识库归属部门已被删除或归档（悬空归属）→ 行为上与「未分类」一致；不报错、不授权。
- **机构节点被归档或删除** → 该隔离边界随之失效，且失效方向必须是**收紧**（AC-20a / AC-20b），不得因归档反而放宽可见范围。
- 祖先部门互为前缀（如同一父节点下的 `1/2` 与 `1/20`）→ 判定不得把其中一个误判为另一个的祖先。
- 标记翻转与列表读取并发 → 不要求强一致快照，但**不得出现「已收紧、旧范围仍长期可见」**。
- 用户同属多个部门，其中部分部门无任何可见知识库 → 并集结果不受影响。
- 节点被标记为「部门」但其父链上从未出现过机构（极端构造）→ 按 AC-14，根节点类型不影响结果，规则仍可判定。
- 某节点的机构/部门标记在其名下有知识库时被改动 → 按 AC-05 先确认、按 AC-06 立即生效，不作静默处理。
- 租户内无任何节点标记为「部门」→ 需求 2 不会产生任何效果（这是 AC-02 的必然推论，属预期行为，见下方「已知缺口」）。

**已知缺口（本期不做，记录待另行处理）**

- **本特性上线后不会自动生效**：AC-02 要求存量节点一律为「机构」，因此客户必须先完成组织树标注，才会观察到需求所述的效果。**标注属交付实施动作**（写入实施清单与验收前置条件），不得被理解为「安装即可用」。本特性提供引导与批量入口（AC-08）以降低该动作的成本，但不代替它。
- **无例外机制**：平台上不存在「某个库排除某个部门」的表达能力。出现此类诉求时，只能通过调整树结构（把该库移到机构节点下，或把相关节点标为机构）解决，代价是影响面可能超出预期。见 INV-20。
- **机构与知识空间的组合**：知识空间不参与本规则（AC-18），而知识空间自身已有成员制。若业务期望「机构内的知识空间也自动互通」，需要另行评估两套授权语义的叠加方式，不在本特性范围。
- **机构归档后的知识库处置**：AC-20a 只规定「归档后不再可见」，不规定知识库本身的去向。F057 有「部门归档 → 其名下知识库回到未分类」的联动（F057 AC-23），但本特性**不复用**该联动——机构归档与知识库归属是两件事。机构名下的知识库是否需要在归档时一并流转，属组织运维决策，本特性不提供自动处置。
