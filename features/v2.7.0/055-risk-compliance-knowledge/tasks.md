## 实际偏差记录

- **T-06 测试修正**：`TestTodayExpression._cond` 原用字面量 `"<="`，与 `ComparisonType.LESS_THAN_OR_EQUAL`（`"less_than_or_equal"`）不符导致 3 例失败；改为引用枚举常量（2026-09-06）。
- **top_k 最终截断加守卫**：design §4.1 流水线写「top_k 截断」无条件执行，但融合结果可能超过 k（两引擎各 k=100 去重后 >100），AC-13 要求未配置时行为不变——实现为「仅当节点显式配置 top_k 时才截断」，未配置保持既有行为。
- **rrf_score 落 doc metadata**：design 决策 3/5 依赖「rrf_score × weight」「RRF 融合后阈值」，但既有 `RRFRerank` 不产出分数——在 `RRFRerank.compress_documents` 末尾写入 `doc.metadata["rrf_score"]`（增量字段，两个既有消费方 KnowledgeRetrieverTool / ensemble_retriever 不受影响；rerank 压缩器 `sort_rerank_result` 复用原 Document，分数在 rerank 后仍可读）。
- **标签过滤逐库解析**：坑 9 口径落地——tags 按 business_id 归属所选知识库逐库解析 file 范围，未选标签的库不受限（避免「A 库标签把 B 库过滤为空」）。
- **weight=0 库在构建 retriever 时即排除**（spec §3「不参与多库检索召回」），`apply_kb_weight` 的丢弃逻辑保留为双保险。
- **时效预过滤降级**：`get_non_effective_file_ids_by_knowledge_ids` 失败（如环境未跑 F055 迁移、未知列）时记 warning 跳过时效过滤，不破坏既有工作流检索——与版本过滤同款 best-effort 口径。
- **T-08 共享纯函数抽离**：4 个辅助函数（resolve_retriever_top_k / combine_document_scope / apply_kb_weight / merge_priority_docs）从 `workflow/common/knowledge.py` 移入 `bisheng/knowledge/rag/risk_compliance_filters.py`——知识域服务不得依赖 workflow 模块（C1），双链路（文档库 / 知识空间）从同一点导入保证口径一致（坑 3）；workflow 侧保留 re-export，T-06 测试导入路径不变。
- **T-08 标签空命中跳过**：tags 选中但该库/空间无任何文件关联 → 跳过该库/空间检索（`document_id in []` 在 Milvus expr 非法；与 metadata filter 无命中跳过的既有约定一致）。T-07 文档库路径同步补上该守卫。
- **T-08 weight map 口径**：weight=0 的库/空间在构建阶段即被排除，且不进 weight map——避免「只选了 weight=0 库」时误触发权重重排守卫，保住默认路径零回归（AC-11）。
- **T-08 空间对象防御读取**：space.weight/priority 用 `getattr(..., 默认值)` 读取——单测用 SimpleNamespace 模拟空间对象，且兼容未跑迁移前的旧代码路径。
- **T-08 范围口径**：assistant / agent 工具的 space 检索入口（`SpaceKnowledgeRetrieverTool` / `build_space_knowledge_tool`）默认不透传 F055 新参数（保持旧行为）；本期仅工作流节点路径（`RagUtils._aretrieve_space_docs` → `aretrieve_space_documents`）注入。
- **T-10 共享构建函数落点**：design 决策 7 的「可复用入口」实现为 `knowledge/domain/services/knowledge_flow_retrieval.py::retrieve_knowledge_documents`（sync——文档库链路本就同步；端点经 `run_in_threadpool` 调用）。RagUtils 的文档库检索逻辑（分组构建/双轮召回/后处理/版本与时效排除/标签解析）整体下沉到该模块；RagUtils 保留 `_knowledge_vector_list` 跨问句缓存（经 `knowledge_vector_list` 参数传入共享函数，避免每问句重建向量库对象/重复模型查询）。`invoke_knowledge_retriever_tool` 同样下沉并被 RagUtils 文件上传路径复用（单一构造点）。
- **T-10 postprocess 收口**：权重/阈值/top_k 后处理抽为纯函数 `postprocess_risk_docs`（risk_compliance_filters），知识库路径、文件上传路径、空间路径三方共用（空间路径优先级合并后传 top_k=None，因 merge 已截断）。
- **T-10 测试口径迁移**：`test_rag_utils.py` 的 8 例 search_kwargs 断言随构建逻辑迁移到新文件 `test_knowledge_flow_retrieval.py`（共享函数层，mock 目标同步下沉）；`test_rag_utils.py` 改为 RagUtils 委托/缓存/文件路径单测；T-06 纯函数测试导入路径从 workflow 模块改为 risk_compliance_filters 直连（workflow 不再 re-export 未使用的纯函数）。
- **T-10 端点口径**：`POST /knowledge/{id}/hit_test` 权限走 `_get_readable_knowledge`（只读端点 → 读权限，AC-17）；`check_auth=False`（权限已在端点层校验，避免重复 OpenFGA 查询）；排除统计由 `KnowledgeFileDao.count_non_effective_files_by_knowledge_id` 提供，谓词与检索过滤同源（docstring 交叉引用）。
- **T-11 级联落点在 DAO 而非 service**：tasks 原定改 `knowledge_service.delete_knowledge_tag`，实现时发现 `TagDao.delete_business_tag` 是文档库与知识空间**两个调用方**共用的删除入口（`knowledge_space_service.py:4234` 同样存在孤儿 TagLink bug）——级联改为在该 DAO 方法内实现（同一事务：业务域 scoped SELECT 校验归属 → 删 Tag → 删全部 TagLink），两调用方同时修复。跨租户防护：两条 bulk DELETE 不享受租户自动过滤（CLAUDE.md 坑），故先走租户自动过滤的 SELECT 校验 tag 归属（business_type+business_id+id 全匹配）再按已验证 id 删除；外域/跨租户 tag_id 零副作用且幂等返回 True（保持既有调用方语义）。
