# 并行子代理流式积压修复（2026-10-18）

## 问题与实现

真实会话 `7d3ad542e4a148e681ba20b9f5064b56` 的任务 `74bfc049f4dd4b1bba06930db86577bb` 中，三个研究子代理在 16:55:49～16:55:59 已保存末尾 AI 回复，但父层事件消费持续到 17:55 以后。旧路径串行等待每个思考 token 的历史缓存更新、数据库节流写入与可靠事件追加，然后才读取下一帧。日志样本含约 5800 次步骤持久化；慢查询记录 1436 条，平均约 500.5ms，耗时总和 718.7 秒。慢查询总和不是任务关键路径耗时，界面工具开始/结束事件之间的间隔也不能直接当成外部工具实际服务延迟。

新增 `stream_event_buffer.py`：

- 在事件持久化前预取并合并思考片段，按 task/call/namespace 保留独立文本，不截断、不丢弃文本。
- 默认 250ms 或累计 8192 字符刷新，队列上限 16 项；队列满时反压，不开无限后台队列。
- 工具调用、工具结果、计划、人工输入和终态均作为顺序屏障，先刷出此前思考文本，原事件保持独立。
- Provider 暂停输出时定时刷新末尾文本；源异常、存储异常、取消或执行租约丢失时关闭读取任务，不留下悬挂生产者。
- 新建、人工恢复、故障恢复和多轮继续统一调用同一消费入口。外部工具恢复回执、执行 fencing、事件 ID 与数据库迁移不变。

## 原会话接续与限制

完成回归后更新本地专用 Linsight Worker，API 与前端未重启。更新前原任务 68 份回执均为 done，无结果未知的 unsafe 调用、无 stateful 沙箱回执；更新后进入 epoch 2，但自动接续仍以 `Task produced no result` 失败。这是本轮暴露的接续收尾问题，性能优化不意味着该问题已修复。

检查点中的主对话为 DeltaChannel 增量存储，不能以单个快照未含 messages 判断丢失。取回三个子代理的真实末尾摘要（4352、4109、3408 字符），通过原会话的受支持 continue 接口提交明确的运行维护接续请求，要求复用已有研究、避免重搜和重复委派，进入 epoch 3 整理文档；没有直接改写数据库任务终态，也未把已有研究伪造成重新运行。最终状态 completed，生成 Word（53963 字节）与 Markdown（33843 字节），通过客户端 :4001 的签名下载均 HTTP 200，MD5 与回执一致，Word ZIP 包含 word/document.xml。报告中的行业数据准确性及文档视觉排版不属于本轮性能验收。
