## 1. 目标与非目标

- **目标**：把「外部业务数据库」接成平台的一种**知识来源**——管理员以配置方式建数据源（连接 + 表 + 业务描述），终端用户在对话里用自然语言问数；系统实时生成 SQL 查询并基于结果作答，与既有文档知识库**同轮共存**、来源可辨、查询可复核。
- **非目标**：
  - **不是**把库数据抽出来灌进向量库（那是另一条产品路线，本特性完全不碰 Milvus/ES）
  - **不是**知识库的新类型（数据源是独立领域对象，`KnowledgeTypeEnum` 不动）
  - **不是**行级权限系统（平台不做行级过滤，见决策 9）
  - **不是**语义层 / 指标口径平台（只到「表 + 字段」的业务描述）

---

## 2. 关键约束

本功能**特有**的硬性约束（决定下面方案对比的取舍空间）：

- **全局架构铁律遵循 `docs/constitution.md` C1–C7，本节不重抄。** 本 feature 的具体落点：
  - **C1**（分层）：新建 `datasource` 三层模块；service 不写 ORM；`common/` 不得 import 领域服务
  - **C2**（双 DB）：新表用 `dialect_helpers.JsonType`（表结构快照、结果快照要存 JSON）/ `LargeText`（SQL 语句可能很长）；**尤其注意**：本特性要连的**外部库**与平台自身的双 DB 约束是两件事——外部库的方言由配置决定，平台的元数据表仍须 MySQL+DM8 双兼容
  - **C3**（多租户）：四张新表均带 `tenant_id`，**且必须登记进租户过滤白名单**（仅带列不够，见 §5 坑 1）
  - **C4**（权限）：数据源创建必须调 `PermissionService.authorize()`、变更前 `check()`（见决策 10）
  - **C5**（错误码）：模块 **117**，已在 v2.7.0 契约登记
  - **C6**（密钥）：连接密码**必须** Fernet 加密，不得明文
  - **C7**（前端）：两个 SPA 的取数均走各自 API 层，store 不调 HTTP
- **运行时依赖（本特性特有）**：
  - **`sqlglot` 当前不在依赖中**（`pyproject.toml` 无、全仓无 import、venv 未装）——需新增
  - **达梦（DM8）在本项目内是被支持的引擎**（`pyproject.toml:71,74` 已装 `dmPython` + `dmSQLAlchemy`，注册 `dm+dmPython://`），但 **`sqlglot` 没有达梦方言** —— 这是本特性最硬的兼容性约束（见决策 7）
- **凭据存储**：平台已有 Fernet 工具（`core/config/settings.py:25-29` 的 `encrypt()` / `decrypt()`），且 F009 已用「Fernet-encrypted JSON」列存过敏感配置——**复用，不自造**
- **容量约束**：单数据源暴露表数无硬上限，但**注入模型的表描述总量有阈值**，超阈值必须退化（见决策 6）
- **性能约束**：单次查询不得阻塞对话事件循环（见决策 12）

## 3. 方案对比与选定

### 决策 1：新建独立 `datasource` 领域对象，不扩展 `KnowledgeTypeEnum`

- **备选**：
  - A. 扩展 `KnowledgeTypeEnum` 加 `DB = 4`，蹭知识库的列表页 / 选择器 / 授权 / 部门归属 —— 复用最多
  - B. 新建独立领域对象 + 独立模块 —— 独立但工作量大
  - C. 只增强既有工作流 Agent 节点的 `sql_agent`，不碰对话侧 —— 最省事
- **选定**：**B**
- **原因**：
  - 走 A 等于**给一个永远空的 Milvus collection + ES index 交房租**：`KnowledgeService.create_knowledge_base`（`knowledge_service.py:683`）强制 mint `collection_name`/`index_name` 并调 `_init_knowledge_indices_sync`，且 `model`（embedding 模型）是必填字段——**数据源没有文档、不切块、不向量化，这些字段对它全是空转**。
  - 走 A 还要背 F055 的 `effective_date`/`expire_date`、`weight`/`priority` 与 F057 的 `department_id`——这些语义套到「数据库连接」上不成立。
  - 走 C 够不着需求：只能在流程编排里用，**终端用户问不了**，而终端用户才是本需求的主体。
- **何时该重新考虑**：若后续出现「数据源和知识库必须在同一个列表页统一管理」的强需求，可再加一层「统一资源入口」，但**不要为此把它们塞进同一张表**。

### 决策 2：数据源以「工具」形态进入对话，**不**做第三类知识库

- **备选**：
  - A. 在 chat 链路里写「选路器」，判断本轮该走文档还是走库 —— 显式可控
  - B. 把数据源做成一种 tool，与知识库检索工具**同层**，让模型自己决定调哪个
  - C. 独立页面，与对话隔离
- **选定**：**B**
- **原因**：
  - **系统里本来就有这个抽象**：工作流 Agent 节点把「每知识库一个 tool」（`tool/domain/services/executor.py:423 init_knowledge_tool_sync`）与 `sql_agent` tool **塞进同一个 `func_tools` 列表**（`workflow/nodes/agent/agent.py:266-268`），再统一包 `WorkflowCitationToolWrapper`。顺着这个已有抽象走，能同时吃到助手 / 工作台 / 客户端三个面。
  - 走 A 的核心问题是**选路一旦错，用户看到的是看似一本正经、实则来源错误的答案**——比让模型多调一次工具代价大得多。
  - 混合来源（spec AC-30）在 B 下是**自然结果**而非额外工程；在 A 下要做两套链路的编排。
- **代价**：选路权交给 LLM，必须接受「模型可能不调、可能调错表」；缓解靠表描述质量（决策 5）+ 回答里明示来源（AC-29）+ 失败治理闭环（决策 13）。
- **何时该重新考虑**：若实测发现模型在多数据源下选错率过高，可加**显式提示**（用户手动指定本轮数据源），但不要退回到自动选路器。

### 决策 3：收敛既有内联 `sql_agent`，做兼容读取而非破坏性替换

- **备选**：
  - A. 共存不迁移：新的独立做，老的内联原样保留
  - B. 收敛：数据源成为唯一入口，老配置做兼容读取
  - C. 直接废弃内联 `sql_agent`
- **选定**：**B**
- **原因**：
  - C 是破坏性变更——**已发出去的流程和两个预制应用**（`database/data/template.json:13305`「⭐️SQLAgent」、`:25152`「⭐️ 查询数据库并画图」）都在用内联配置，会直接炸。
  - A 把**明文密码**这条安全债留在用户最先找到的那条路上；而 B 让凭据加密与 schema 治理**各自只有一个地方要做**。
  - 兼容读旧的 `node_params["sql_agent"]` 即可让既有流程不炸；同时**关闭内联新建**（AC-56），使存量只减不增。
- **何时该重新考虑**：待预制应用与存量流程全部迁移后，可评估彻底移除内联分支。

### 决策 4：仅做实时 NL2SQL，**不**做「抽数灌向量库」

- **备选**：
  - A. 实时 NL2SQL：配置连接 + 选表 → 读 schema → 生成 SQL → 实时执行
  - B. 灌库：抽表数据 → 切块 → 向量化 → 走既有 RAG
- **选定**：**A**
- **原因**：
  - 需求方的原始表述是「**库和表都是配置对接进来的**」——既然是配置连接、选表，说明数据是**活的、结构化的、要算的**，这正是向量库的短板：切碎的数字行检索出来**没法做聚合**（「上季度华东区销售额」在 RAG 下答不出来）。
  - B 只在「要快照、要跨库混合检索、要离线可用」时才成立，本需求不具备这三个前提。
- **何时该重新考虑**：若出现「要把库数据与文档一起做语义检索」的需求，那是**另一个 feature**（且与本特性共享「数据源」对象，本特性应作为其上游 Owner）。

### 决策 5：表结构快照落库 + 人工补业务描述 + 手动重采集；**不做**运行时反射、**不做**定时采集、**不做**样例值采样

- **备选**：
  - A. 纯运行时反射（agent 每轮自己 `list_tables` / `describe`）—— 零工作量（= 现有 `sql_agent` 的形态）
  - B. 建源时采集快照 + 人工补描述 + 手动重采集
  - C. B + 定时自动重采集
  - D. B + 表内真实数据采样（样例值喂模型）
- **选定**：**B**（D 的按列 opt-in 留作后续，本期不做）
- **原因**：
  - **A 不是「省事」而是「会坏」**：其一，每轮都要 list_tables→schema 来回，表一多直接爆 context；其二，业务库里字段常是 `f_0031`、`col_05`，**没有人工描述模型只能猜**——现有 `sql_agent` 就是 A，它的实际效果就是这条路的证据。
  - **C 的代价是踩已知坑**：CLAUDE.md §Known Pitfalls 点名 **Celery Beat × 多租户**，而自动重采集正是「定时任务 × 每租户每数据源」。表结构变更是低频事件，人工点一下足够；真要做好的是「查询时发现漂移就提示重新采集」，无状态、无定时任务。
  - **D 有隐私面**：采样等于**把真实数据行送进 prompt**，可能带出姓名、手机号、金额。若要做，必须**按列 opt-in**，而不是全表默认。
- **何时该重新考虑**：D 的触发条件是「客户明确接受数据采样且需要枚举值语义」（如 `status` 到底是 `1/2/3` 还是 `'active'`）。

### 决策 6：全量注入 schema，超阈值退化为「表描述可检索」

- **备选**：
  - A. 保留 agentic 探索（模型每轮自己探）
  - B. 全量注入 curated schema，单次生成
  - C. 表清单 + 一句话描述常驻，需要细节时检索对应表的完整字段
- **选定**：**B 打底，超阈值退 C**
- **原因**：
  - **A 与决策 5 直接冲突**：agentic 探索读到的**恰恰是库里那些烂字段名**，读不到管理员辛苦填的业务描述——等于把决策 5 的工作量白扔。
  - **B 是 curated schema 的必然形态**：管理员选了表，就是**声明了「这些表要被问」**，那它就该直接被模型看见，不需要模型自己找。
  - **B 有明确崩点**：表一多（如 50 张 × 30 字段）prompt 直接爆。阈值取值属实现参数，**初始按「单源 ≤ 30 张全量注入」**。
- **可观测口径（落地 spec AC-28）**：两种注入形态必须可区分，具体三处：
  1. **执行记录**（`db_query_log`）落一行注入形态标记（`inject_mode = full | retrieved`），与本次查询同生命周期；
  2. **结构化日志**在退化时打印一次（阈值、实际表数、命中检索的表名集合），供 __log__ 分析；
  3. **响应/引用锚点**携带形态标记，使前端与 e2e 无需读日志即可断言。
  三者共用同一枚举，**不各自造名**。无此口径则「阈值」只是拍脑袋的参数，无法按 AC-28 的意图标定与回归。
- **何时该重新考虑**：阈值需在真实数据上标定；若常见场景就是上百张表，C 会成为主路径而非退化路径。

### 决策 7：SQL 安全校验用「`sqlglot` AST 严格档 + 关键字窄校验兜底档」双层，**解析失败不等于拒绝执行**

- **备选**：
  - A. 新引入 `sqlglot`，AST 校验；解析不了就拒绝
  - B. 自写窄校验（单语句 + 首关键字 SELECT/WITH + 禁写关键字）
  - C. A + B 叠加：能解析走 AST，解析不了退 B 并记录
- **选定**：**C**
- **原因**：
  - **A 在达梦上会误杀**：`sqlglot` **没有达梦方言**，只能拿 `oracle` / `mysql` 方言去凑；达梦特有语法（`ROWNUM`、`(+)` 外连接、DM 专有函数）可能解析失败——若失败即拒绝，**达梦数据源基本不可用**，而达梦恰是本项目最可能遇到的库（`pyproject.toml:71,74` 已装驱动）。
  - **B 单独用太松**：挡不住「SELECT 里套函数副作用」这类 AST 级绕过。
  - C 让两边各得其所。**关键约束**：C 意味着**存在「较宽松的校验档」**，所以 AST 档**不能是安全性的唯一依赖**——真正的边界是只读账号 + 只读会话（决策 8）。
- **附带**：`sqlglot` 多方言解析同时解决了「不同引擎生成的 SQL 分页/日期函数差异」的提示词问题。
- **何时该重新考虑**：若 `sqlglot` 对达梦的误判率高到影响可用性，应评估**为达梦单独写一个更贴合的窄校验**，而不是放宽整体策略。

### 决策 8：只读边界 = 只读账号（首要）+ 只读会话 + 平台校验（兜底）；**可写账号只警告不阻断**

- **备选**：
  - A. 只靠提示词（现有 `sql_agent` 就是这么干的）—— 等于没有护栏
  - B. 平台侧强制解析 + 行数/超时/截断
  - C. B + 只读会话（`SET TRANSACTION READ ONLY`，不支持则降级）
  - D. C + 执行前人工确认
- **选定**：**C**；账号校验取 **B（只警告不阻断）**
- **原因**：
  - **D 会杀死体验**：用户要的是「问答」不是「审 SQL」。会写 SQL 的人不需要确认，不会写的人看不懂确认框，点「同意」变肌肉记忆——护栏价值归零，而 B+C 已在服务端挡住真正的破坏。
  - **强校验只读账号（拒绝保存）会让功能在客户现场不可用**：现实里客户 DBA 经常不给新建只读账号（要走审批）。硬性要求的结果不是更安全，而是**客户用不了或绕过去**。
  - **唯一可靠的只读边界是数据库自己（账号权限）**；平台解析只是兜底。这条必须写死，避免后人误以为 AST 校验是安全边界。
- **何时该重新考虑**：若客户环境能强制只读账号，可升级为「拒绝保存」，届时 AC-05 需同步修改。

### 决策 9：平台**不做**行级过滤；安全责任落在「账号权限 + 授权治理」

- **备选**：
  - A. 账号权限即边界（零成本）
  - B. 平台强制行级过滤（注入条件 + AST 校验模型 SQL 未绕过）
  - C. 收窄授权：只授权给本来就有全量数据权限的角色
  - D. C 打底，B 紧随
- **选定**：**C**（经用户明确确认）
- **原因**：
  - 用户确认使用群体本来就有全量数据权限（风控 / 财务分析岗），B 的成本（AST 层校验模型是否绕过注入条件——子查询改别名、`UNION`、`OR 1=1` 都要防）在本期不划算。
  - **必须在 design 里写明的代价**：C 的安全性**完全由「授予动作掌握在谁手里」决定**。今天只发给财务分析岗是安全的；明天有人把它发给「全体用户」，行级差异立刻回来，**平台侧没有任何东西会拦住**。此风险已在 spec §3 与契约 INV-19 ④ 显式声明。
- **何时该重新考虑**（**触发条件明确**）：一旦出现「同一批人里有人只该看部分行」的场景，B 必须做，且必须是**平台强制**而非提示词约束。届时回写 INV-19 ④。

### 决策 10：数据源在 FGA 授权模型中**新增一类受控资源类型**，而非复用 `tool` 或 `knowledge_library`

- **备选**：
  - A. 复用既有 `tool` 类型（数据源作为工具行）—— 零模型变更
  - B. 复用 `knowledge_library` 类型 —— 蹭知识库授权形状
  - C. 新增独立资源类型 —— 需改 FGA 模型
- **选定**：**C**
- **原因**：
  - **A 与 spec AC-43/AC-44 冲突**：数据源需**独立权限点**（谁能创建/管理数据源与谁能创建知识库相互独立）。若复用 `tool`，数据源的授权将由 `tool` 类型的元组与 `_MANAGE_PERMISSION_BY_RESOURCE['tool']` 决定，**无法独立治理**；且 `tool` 的列表口径会把数据源混进工具管理页。
  - **B 与 spec AC-61/AC-64 冲突**：数据源明确不进知识库体系、不修改知识库授权形状。
  - **C 的实现成本已被摸清**（见 §4.3 与 §5 坑 2–3）：模型定义在 `core/openfga/authorization_model.py`，资源类型用 `_standard_resource_type()` 工厂**一行一个**；F013 已为 F020 **预分配过** `llm_server`/`llm_model`（`authorization_model.py:292-296`），**证明「在模型里加类型」是本项目走过并被认可的路子**。
  - 还需配套：`permission_schema.py:8` 的 `VALID_RESOURCE_TYPES` 闭集、`resource_permission.py:162` 的 `_MANAGE_PERMISSION_BY_RESOURCE` 映射，以及一份参照 `knowledge_library_permission_template.py` 的权限模板。
- **何时该重新考虑**：不需要重新考虑——这是 spec 已确认的硬需求（AC-43）。

### 决策 11：SQL 生成用**独立模型槽位**，未配置则回退对话模型

- **备选**：
  - A. 复用当轮对话模型 —— 零配置
  - B. 独立租户槽位（`nl2sql_model`）+ Root 回退
  - C. 每个数据源各配一个模型
- **选定**：**B**
- **原因**：
  - **两个难度档**：写对多表 join 与组织答案是两种能力，绑在一起等于**逼二者互相将就**。
  - **合规是更硬的理由**：生成 SQL 意味着**把表结构（含人工补的业务描述）送进模型**。银行/信创场景很可能要求这步走**私有化部署的模型**，而对话可以走别的——若只有 A，本能力在这些客户处直接不可用，**而这恰是这类客户最想要的场景**。
  - 机制现成：`tenant_system_model_config` 按 key 存 model_id 且带 Root 回退（`llm/domain/models/tenant_system_model_config.py:77-126`）；槽位取值须满足 **INV-8**（本租户可见 + model_type 匹配）。
  - 走 C 没人配，且与数据源数量相乘。
- **兜底口径**：槽位未配置 → **回退当轮对话模型，不报错**（可用性优先，spec AC-27）。

### 决策 12：数据源查询必须异步；重写既有 `sql_agent` 时一并修掉阻塞缺陷

- **备选**：
  - A. 沿用既有 `SqlAgentAPIWrapper`（同步）—— 零改动
  - B. 重写为异步执行路径
- **选定**：**B**
- **原因**：
  - 既有实现 **`run` 是同步的，`arun` 直接委托 `run`**（`bisheng_langchain/gpts/tools/sql_agent/tool.py:75-76`）——**会阻塞整个事件循环**。对话侧一旦有并发，一个慢查询会把同一进程内**所有**对话请求卡住（spec AC-21）。
  - 既然决策 3 已决定收敛重写，这条**顺手修**，不单独排期。
- **何时该重新考虑**：不需要——这是已确认的既有缺陷。

### 决策 13：失败回喂重试（≤3 轮）+ 失败留档反哺描述治理

- **备选**：
  - A. 不重试
  - B. 出错把 DB 报错回喂给模型修正，重试 2–3 轮
  - C. B + 失败提问留档给管理员
- **选定**：**B + C**
- **原因**：
  - **A 在真实场景会大量失败**：模型对烂字段名一次猜中是小概率事件，而 **DB 报错信息本身就是最好的纠错信号**——这个信号现在被完全丢掉。
  - **B 的成本几乎为零**：决策 7 已定要走解析管道，重试循环正好插在「生成 → 解析 → 执行 → 报错回喂」这条已有管道上。
  - **C 是真正的杠杆**：决策 5 让管理员补业务描述，但**补哪张表、补哪个字段的依据从哪来**？只能从失败里来。没有 C，决策 5 就只是一张填空表；有 C，它才是闭环。
  - **必须封顶 3 轮**，否则一个必然失败的问题会烧满 token 与时间。
- **留痕边界**：失败留档**只存语句与错误类别摘要，不存结果集、不存用户提问原文**（遵守 INV-11 / INV-19 ③）。

### 决策 14：工作流侧只收敛 Agent 节点，**不**新增独立检索节点

- **备选**：
  - A. 只走 Agent 节点（把内联配置换成「选数据源」）
  - B. 再新增与 `knowledge_retriever` 并列的「数据库检索」节点
  - C. A + B
- **选定**：**A**
- **原因**：
  - **B 是第二条执行路径**：新节点要注册进 `node_manage`、新增前端节点组件 + 配置面板、新增三语 i18n、还要考虑老版本流程兼容——成本是 A 的数倍，而**它买到的东西 A 已经买了**（Agent 节点里同样能调数据源）。
  - B 真正独有的价值只有一个：在流程里**确定性地**执行一次「问题 → SQL → 数据」，不依赖模型决定要不要调工具。该价值真实但场景少，**可晚一轮加**。
- **何时该重新考虑**：编排者对结果确定性有硬要求时。

## 4. 系统现状（接手必读）

### 4.1 数据流

#### 建源与元数据采集（管理员侧）

```
管理员填连接信息 → 测试连接（不落库） → 列出可访问表 → 勾选暴露范围
  → 采集表结构快照（表名/字段名/类型/库内注释）→ 管理员补业务描述 → 保存
  → [手动] 重新采集：只刷新结构快照，不覆盖人工描述
```

#### 问答侧（终端用户）

```
用户提问（已选数据源）
  → 表描述注入（全量；超阈值退检索）
  → 模型决定调用数据源工具
  → 生成 SQL → sqlglot AST 校验 / 窄校验兜底
  → 只读会话执行（行数上限 + 超时）
  → [失败] DB 报错回喂 → 重试（≤3）→ [仍失败] 留档 + 以其他来源作答
  → 结果行 + 语句 → 模型组织答案
  → 回答（来源标注 + 可折叠 SQL/结果表，随消息持久化）
  → 执行记录留痕（语句 + 状态，不存结果集）
```

#### 既有 NL2SQL 的位置（本特性要收敛的对象）

```
工作流 Agent 节点
  → node_params["sql_agent"]（内联：引擎/地址/库名/账号/明文密码）
  → agent.py:400 _init_sql_address() 拼 SQLAlchemy URI
  → load_tools({"sql_agent": {llm, sql_address}})
  → SqlAgentAPIWrapper：SQLDatabase.from_uri → SQLDatabaseToolkit → create_react_agent
  → 硬编码系统提示（只读 SELECT、≤50 行）【提示词级，非强制】
```

## 7. 测试与可观测

- **单元**：SQL 校验器（AST 档 + 窄校验档 + 降级路径）、schema 注入的阈值退化、凭据加解密、租户隔离、重试循环的封顶。
- **集成**：数据源 CRUD + 测试连接（可用 aiosqlite/mock 或 CI 的真实引擎容器）、表结构采集、执行记录与失败留档的写入。
- **不许 mock 掉的**：只读账号拒绝、行数上限截断、超时中断——这三条是安全边界，必须有真实或高保真的验证。
- **DM8 / 多引擎**：**在 CI 跑**，不依赖本地（`docs/SDD-Guide.md` §6）。达梦的**库内注释可采性**是本特性必须实测的第一项（spec AC-14）。
- **手动验证一遍（可操作路径）**：
  1. **起服务**：后端 `uv run uvicorn bisheng.main:app --host 0.0.0.0 --port 7860 --workers 1 --no-access-log`；platform 前端在 `src/frontend/` 下 `pnpm start -- --host 0.0.0.0`（dev :3001）；client 前端为 :4001（base `/workspace`）。
  2. **准备库**：在测试库上建一个**只读账号**连接（不要用可写账号——那会绕过本特性的首要安全边界，测不出真问题）。
  3. **建源调通**：platform → 数据源管理 → 新建 → 选引擎/填连接 → **[测试连接]** 必须成功。
  4. **勾表 + 补描述**：勾 2–3 张业务表，**至少给一张表填业务描述**（不填测不出 schema 治理的价值）；再触发一次 **[重新采集]**，确认人工描述**未被覆盖**（AC-12）。
  5. **对话侧提问**（助手或 client :4001）：
     - 问一个**能走库**的问题 → 回答应明示来源（AC-29）、引用锚点含表名 + SQL（AC-31）、展开可见结果表（AC-32）；
     - 问一个**能走文档**的问题 → 确认文档来源标注正常；
     - 问一个**两者都要**的问题 → 确认两类来源在一条回答内共存（AC-30）。
  6. **刷新页面 / 换端**：展开区与引用锚点应仍在（AC-34）。
  7. **失败路径**：问一个**表里没有的字段** → 应看到重试后仍失败的说明（不暴露库结构，AC-39），且该轮文档来源若命中应仍作答（AC-40）；随后到管理端失败清单应能查到该次（AC-41/42）。
  8. **观测**：查 `db_query_log` 有执行记录且**无结果集数据**（AC-23/65）；构造一个超阈值的大数据源，确认注入形态降级被记录（决策 6 的可观测口径）。
  9. **回归**：老流程里带内联 `sql_agent` 配置的那个预制应用，**必须仍能正常跑**（AC-54）。
- **自动化门禁**：后端 `uv run pytest test/datasource/`（新增测试放 `test/datasource/`，不放 `test/` 根）；前端 `pnpm lint` + `pnpm typecheck`（从 `src/frontend/` 跑，CI `frontend-quality.yml` 强制）。
- **关键日志**：查询降级（只读会话不支持 / 方言解析失败）、被安全策略拒绝的语句、重试次数达到上限、**schema 注入形态退化**（阈值 / 实际表数 / 命中检索的表名集合，见决策 6）。

## 9. 实施顺序（关键）

> 依赖关系决定顺序；标 **[前置]** 的必须先落地，否则后续全部返工。

1. **[前置] 定 §8 待定项 1（FGA 模型升级路径）** —— 它决定权限层怎么写、以及升级客户能否用
2. **[前置] 实测达梦库内注释可采性** —— 决定 AC-14 的界面口径是不是达梦的必经路径
3. 错误码 117 + 四张表 ORM/DAO（**含租户白名单登记**，坑 1）
4. 权限接入：FGA 类型 + `VALID_RESOURCE_TYPES` + `_MANAGE_PERMISSION_BY_RESOURCE` + 权限模板（决策 10 配套）
5. 数据源 CRUD + 测试连接 + 表结构采集（含凭据加密）
6. SQL 校验器（双层 + 降级）—— **先写测试**，这是安全边界
7. 执行器（异步、只读会话、行数/超时、重试回喂 ≤3）
8. 数据源工具形态 + schema 注入（含阈值退化）
9. **平台管理端 UI**（spec AC-57，platform SPA）：数据源列表与创建/编辑表单（含引擎下拉、测试连接按钮）、表勾选、表描述维护、重新采集触发、授权管理入口、失败提问清单页。**这一步常被漏掉**——它不依赖对话链路，可与 6–8 并行。
10. **[前置 定案后] 助手/工作台/客户端绑定**（§8 待定项 2）
11. 引用锚点 + 结果持久化 + **客户端回答区展示**（展开 SQL/结果表 + 下载 + 引用锚点，spec AC-58/59）——client SPA 独立实现，**不与 platform 共享组件**
12. 工作流 Agent 节点收敛 + 兼容读取
13. 失败清单 + 治理闭环

> **前端工作量提示**：步骤 9（platform 管理端）与步骤 11（client 回答区）是**两个不同技术栈的 SPA**（platform = Zustand + react-query v3 + bs-ui；client = Recoil + react-query v4 + shadcn），引用锚点与展开区**无法共享组件**，必须各写一遍。这是本特性最容易被低估的一块，排期时不要按「一个前端任务」估。
