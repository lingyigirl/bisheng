## 1. 条款原文与我方口径

> **1. 支持多渠道发布与任务触发：可一键发布至API、Agent Portal等渠道；定时/事件触发；手动或自然语言生成定时任务。**

| 条款要素 | 我方口径 |
|---|---|
| 定时触发 | 为应用（助手/工作流）配置 **cron 周期**（分钟粒度）或**一次性绝对时间**；平台按计划自动运行 |
| 事件触发 | 行内系统持服务账号密钥调用 `POST /api/v2/schedule/trigger` 触发指定任务（防重放 + 频率护栏） |
| 手动生成定时任务 | 控制台「对外发布 → 定时任务」表单：选应用、计划、运行身份、预设输入 |
| 自然语言生成定时任务 | 一句话描述 → 平台生成**草稿**（人类可读计划 + 下次运行时间）→ **人工确认后**才保存 |
| 多渠道发布（前半段） | 见 `开放API条款验收表.md`；本表不覆盖 |

### 1.1 对客可表述的口径（可直接引用）

> 平台已实现定时任务能力（**本机验证通过**：单元/契约 209 用例、端到端 10 用例、真库建表核对）：
> 支持按 cron 周期或一次性时间**自动运行**智能体应用，支持行内系统经 **API 事件触发**（服务账号密钥 + 防重放 + 频率限制），支持**手动配置**与**自然语言生成草稿后人工确认**两种生成方式。
> **需一并说明的三点**：① 事件触发依赖开放 API 强制鉴权总闸（`open_api.enforce_keys`），需在行内环境显式打开；② 定时/事件触发在应用**未上线时不执行**（与按需调用面不同）；③ 事件触发**只返回受理与运行标识**，运行结果在平台任务列表/监控查看，不提供外部查询接口。

## 2. 验收表（现场逐条执行并填写"实际结果"）

> 前置：完成（四）3 的切换（总闸打开）并至少建好一个服务账号与密钥；准备一个在线助手或工作流应用。

**前置条件对照（三件事各自管什么、哪些行需要）**

| 条件 | 作用 | 哪些验收行需要 | 怎么开 | 生效时机 |
|---|---|---|---|---|
| **部署总闸** `open_api.enforce_keys`（后端配置文件） | 关 = 完全旧行为（连密钥都不校验）；开 = 带密钥的调用一律校验 | （四）3 全部鉴权行 + 本表 **E/F/G/H**（事件触发） | 在**后端实际加载的**配置里写 `open_api: {enforce_keys: true}`（源码运行 = `config.<env>.yaml`；容器 = 挂载的 `config.yaml`），随后**重启后端** | 重启后 |
| **租户开关**（默认租户那一行） | 只决定「**不带密钥**的请求」是否被拒（guest 端点与免登录开关除外） | **仅（四）3 的"匿名 → 401/11801"行**；本表**不需要** | `PUT /api/v1/open-api/settings {"enforce_keys": true}`（管理员令牌；匿名判定只看默认租户=1 那行）。**或**在目标环境 `config.yaml` 写 `open_api.default_tenant_enforce_keys: true`（启动时若该行缺失则播种，已有行不覆盖） | ≤5 秒，**不用重启** |
| **Celery beat** | 每 20 秒发布一轮调度扫描 | 本表 **D**（到点自动执行）、**I**（下线跳过/等待上线）、**J**（连续失败自动停用，需多轮） | 启动 `celery -A bisheng.worker.main beat`；同时须有一个消费默认队列的 worker（`-Q celery`） | 启动即生效；**同一 broker 只允许一个 beat**（多实例会重复触发） |

> 三者的关系一句话：**总闸**决定"带密钥的调用认不认"，**租户开关**决定"不带密钥的调用放不放"，**beat** 决定"计划轮次跑不跑"。A/B/C/K/L 行不需要任何开关（管理面与生成链路），L 行的运行动作需已有运行发生（D/E/J 之一）。

| # | 条款要素 | 验收动作 | 通过标准 | 实际结果 |
|---|---|---|---|---|

| B | 手动生成（一次性） | 新建一条「一次性」任务，选一个未来时间 | 保存成功；到达时间后执行一次，任务**自动停用** | ☐ 通过 ☐ 不通过<br>记录： |
| C | 自然语言生成 | 在新建弹窗的 NL 输入框写「每个工作日早上 9 点跑一次」→「生成草稿」 | 返回草稿：计划解释为「工作日 9:00」、回显下次运行时间；**草稿未保存**（列表里没有）；点保存后才出现 | ☐ 通过 ☐ 不通过<br>记录： |

| E | 事件触发（受理） | 用密钥调 `POST /api/v2/schedule/trigger`：头带 `Authorization`、`X-Bs-Timestamp`（当前秒）、`X-Bs-Nonce`（随机串），体 `{"task_id":<id>}` | HTTP 200，`data.run_trace_id` 非空；列表很快出现一次运行结果 | ☐ 通过 ☐ 不通过<br>记录： |
| F | 事件触发（拒绝面） | ① 不带密钥调；② 同一个 nonce 再调一次；③ 时间戳改成 ±1 小时；④ 请求体加一个 `app_id` 字段 | ① **401/11801**；② **400/11912**（防重放）；③ **400/11912**；④ **400/11916**（白名单外字段） | ☐ 通过 ☐ 不通过<br>记录： |

| L | 审计 | 创建/启停/立即运行各一次后，在平台「审计日志」按模块「定时任务」筛选 | 可见创建/启停/立即运行条目；**逐轮运行记录不在**审计页（只落库取证，按 `auditlog.action='schedule.run'` 检索） | ☐ 通过 ☐ 不通过<br>记录： |
| M | 纳管智能体定时任务（F078，`app_type=100`） | 先在「智能体纳管」登记并上线一个智能体，再到详情 → 定时任务 → 建 cron/一次性 → 立即运行 | 任务创建成功；运行结果写入 `managed_agent_run` 与统计；智能体下线/停用后按 F077 口径跳过/拒绝；外部智能体与原生代理均可调度 | ☐ 通过 ☐ 不通过<br>记录： |

> 说明：
> - "119xx"为我方统一错误码（响应体 `status_code`），事件触发面同时返回**真 HTTP 状态**；完整错误表见 [`api/scheduled-task-trigger.md`](api/scheduled-task-trigger.md) §3.1。
> - **授权档位**：运行身份必须是**服务账号专用身份**，且该账号对目标应用有 **editor（可编辑）档及以上**；只授"可查看"会导致任务创建被拒（11905）。
> - **运行身份锁定**：任务创建后运行期不可改变；编辑任务时可更换（会重走同一套校验）。
> - **结果可见性**：定时运行**不产生应用会话**（助手与工作流一致），结果只看任务列表与监控——这是与"手动打开应用对话"的刻意区别。
> - **行 D/E/H/J** 会真实触发应用运行，消耗模型调用；建议用轻量应用验收。

## 3. 本次不在声明范围内（避免验收时口径错位）

| 项 | 说明 |
|---|---|
| 事件触发的"事件源"本体 | 平台只提供**触发端点**（由行内系统在事件发生时调用）；平台不订阅行内消息总线/文件系统等事件源 |
| 外部运行结果查询接口 | 不提供；运行结果在平台侧查看（见说明） |
| 任务级时区 | 统一使用服务器时区（Asia/Shanghai） |
| 任务级自动重试 / 排队 | 不提供；失败等待下一个计划周期自然重试 |
| 含多个人工输入节点或文件类输入的应用 | 一期不支持定时化（创建时明确拒绝，11914） |
| "Agent Portal" 具名渠道 | 平台无此具名渠道；发布渠道见（四）3 验收表 |
