## 2. 配置文件全景

先看一张总表——**重点是「谁读它」和「何时生效」两列**：

| 文件 | 类型 | 谁读 | 生效时机 |
|------|------|------|---------|
| `docker/docker-compose.yml` | 编排 | docker compose | `up -d`（重建容器） |
| `docker/docker-compose.override.yml` | 编排覆盖 | docker compose（**默认发现流程**） | 同上 |
| `docker/docker-compose-ft.yml` | 编排（独立） | 手动 `-f` | 手动 up |
| `docker/docker-compose-office.yml` | 编排（独立） | 手动 `-f` | 手动 up |
| `docker/bisheng/config/config.yaml` | 应用配置 | **容器内**后端（挂载到 `/app/bisheng/config.yaml`） | 重启容器/进程 |
| `src/backend/bisheng/config.yaml` | 应用配置 | 源码运行的后端（默认文件名） | 重启进程 |
| `src/backend/bisheng/config.local.yaml` | 应用配置（本机私有） | 源码运行，需显式 `config=` 指定 | 重启进程 |
| `src/backend/bisheng/config.celery-private.yaml` | 应用配置（本机私有） | 本机 `bisheng-dev.sh` 默认用它 | 重启进程 |
| `src/backend/bisheng/initdb_config.yaml` | **配置种子** | 后端首次启动写 DB，之后**不再读** | 仅首次建库时 |
| `src/frontend/.env.development` / `.env.production` | 前端 env | **client** 的 vite | 构建期 / dev server 启动 |
| `src/frontend/platform/.env.production` / `.env.development.local` | 前端 env | **platform** 的 vite | 构建期 / dev server 启动 |
| `data/backend.env` | shell 环境变量 | `manage.sh`（`source`） | 启动脚本执行时 |
| `data/bisheng-dev.env` | **启动脚本开关** | `bisheng-dev.sh` | 脚本执行时（不传后端） |
| `src/backend/bisheng/core/prompts/yaml/*.yaml` | 运行期数据 | `core/prompts/prompt_loader.py` | 进程启动时全量加载 |
| `src/backend/bisheng_langchain/{rag,gpts}/config/*.yaml` | 运行期数据 | 各自模块硬编码路径 | 调用时读取（见 §2.4） |
| `.github/workflows/*.yml` | CI | GitHub Actions | 触发条件命中时 |
| `.drone.yml` | CI | Drone（内网流水线） | 打 tag / 分支时 |
| `.pre-commit-config.yaml` | 本地钩子 | `pre-commit` | `git commit` 前 |

按层展开：

### 2.1 编排层：docker compose 家族

**`docker-compose.yml`（主编排，9 个服务）**：MySQL / Redis / OpenFGA（含 migrate 一次性容器）+ Milvus 三件套（etcd + minio + milvus）+ Elasticsearch + backend + backend_worker + frontend。它的三处关键写法：

- `environment:` 段里的 `BS_*` 变量 → 由容器内 `/app/bisheng/config.yaml` 的 `!env ${BS_XXX}` 占位符消费（见 §3.1）；
- `volumes:` 把宿主机 `docker/bisheng/config/config.yaml` 挂到 `/app/bisheng/config.yaml`——**容器里跑的是这个文件，不是镜像里那份**；
- `command: sh entrypoint.sh api` / `sh entrypoint.sh worker`——同一个镜像，靠第一个参数决定角色。

**`docker-compose.override.yml`（本机覆盖）**：Compose 在**默认发现流程**下会自动把 `docker-compose.override.yml` 合并进主文件。本机用它做三件事：

1. **端口重映射**（6379→6380、8080→8085、8081→8086），因为本机这些端口被其他项目占着；
2. **MinIO 镜像换 tag**（原 tag 已从 Docker Hub 下架）；
3. **ES 镜像换成官方 `elasticsearch:8.11.3`**（原 bitnami 镜像在本网络拉不动）。

⚠️ 两个必须知道的规则：

- **列表字段是「追加」不是「替换」**，所以重映射端口/卷必须加 `!override` 标签（需要 Compose ≥ 2.24）：
  ```yaml
  redis:
    ports: !override          # 不加 !override 会变成 6379 和 6380 都发布
      - "6380:6379"
  ```
- **显式指定 `-f` 时不会自动合并 override**。已实测：

  ```bash
  cd docker
  docker compose config                  | grep -c 6380   # → 命中：override 已合并
  docker compose -f docker-compose.yml config | grep -c 6380   # → 0：override 被忽略
  ```

  因此 `docker/deploy.sh`（内部写死 `docker compose -f docker-compose.yml`）在本机**不会**读到 override，直接用它 `up` 会撞端口。本机请用 `docker compose -p bisheng up -d`。

**两个可选的独立编排文件**：`docker-compose-ft.yml`（模型微调，需要 NVIDIA GPU）、`docker-compose-office.yml`（OnlyOffice 文档预览，:8701）。它们**不在主编排里**，按需单独启动：

```bash
cd docker
docker compose -f docker-compose-ft.yml -p bisheng-ft up -d      # 微调服务
docker compose -f docker-compose-office.yml -p bisheng-office up -d  # 文档预览
```

**中间件自己的配置文件**（被上面这些 compose 以 volume 挂进容器）：

| 文件 | 挂载到 | 作用 |
|------|--------|------|
| `docker/mysql/conf/my.cnf` | `/etc/mysql/my.cnf` | MySQL 字符集/超时等 |
| `docker/redis/redis.conf` | `/etc/redis.conf` | Redis 持久化与内存策略 |
| `docker/nginx/{nginx.conf,conf.d/}` | `/etc/nginx/…` | 前端容器：:3001 静态资源 + `/api` 反代 `backend:7860` |
| `docker/office/…` | OnlyOffice 插件与 supervisor 模板 | 文档预览前端插件 |

### 2.2 后端配置层（三个 yaml 的分工）

| 文件 | 定位 | 是否入库 |
|------|------|---------|
| `bisheng/config.yaml` | **默认主配置**。源码运行时不指定 `config=` 就读它 | 入库（`.gitignore` 里列了它，但因为已被跟踪，忽略规则实际无效——改它请当作改代码） |
| `bisheng/config.local.yaml` | 本机私有配置，`config=config.local.yaml` 时使用 | 不入库（`config.*.yaml`） |
| `bisheng/config.celery-private.yaml` | 本机私有：**独立 celery broker 分库 + 独立 linsight 队列命名空间**，避免和同事抢同一队列 | 不入库 |
| `bisheng/initdb_config.yaml` | **种子文件**，不是运行时配置——见 §3.1 第 2 层 | 入库 |

三个私有文件的差异本质只有地址与命名空间：`config.celery-private.yaml` 把 `celery_redis_url` 指到别的 db、给 `linsight_conf.queue_namespace` 起了私有名，其余结构与主配置一致。

**顶层键有白名单**：`load_settings_from_yaml` 会校验每个顶层键是否存在于 `Settings.model_fields`，**写错一个键名进程直接起不来**（`KeyError: Key xxx not found in settings`）。典型踩坑：灵思配置的顶层键是 `linsight_conf`（对应 `Settings.linsight_conf`），不是 `linsight`——`linsight` 是 **DB 里**那个块的名字。两者同名不同层，非常容易混。

### 2.3 前端配置层（`.env.*` 的坑）

两个 app 的 **envDir 不同**，这决定了 `.env` 文件放哪儿：

| app | envDir | 因此它会读 |
|-----|--------|-----------|
| client | `path.join(__dirname, '..')` = `src/frontend/` | `src/frontend/.env.development`、`src/frontend/.env.production` |
| platform | `path.resolve(__dirname)` = `src/frontend/platform/` | `src/frontend/platform/.env.*` |

推论（都容易踩）：

- `src/frontend/.env.development` 里的 `VITE_DEV_API_TARGET` **platform 完全看不到**；
- platform 目录下没有 `.env.development`，开发模式只加载 `.env.development.local`；
- `.env.production` 同时服务 `vite build` 和 `vite preview`——这就是为什么本机 `manage.sh` 用 `vite preview` 起前端时，改的仍是 `.env.production`；
- Vite 只把 `VITE_` 前缀的变量暴露给 `import.meta.env` / `loadEnv`。仓库里的业务变量都带这个前缀（`VITE_DEV_API_TARGET`、`VITE_MINIO_PROXY_TARGET` …），**加新变量时忘了前缀 = 静默读不到值（变成 undefined，不报错）**。

**前端变量与后端的强耦合**（改一个必须改另一个，否则 403）：`VITE_MINIO_PROXY_TARGET`（或 client 的 `VITE_DEV_MINIO_TARGET`）的 `host:port` **必须等于**后端 `object_storage.minio.sharepoint`。MinIO 预签名 URL 用 SigV4 签了 `Host` 头，代理转发时 Host 不一致 → 全部 `SignatureDoesNotMatch`（403）。两个 vite.config 里都内置了 403 的提示插件，就是为这个坑加的。

### 2.4 运行期数据类 YAML

这三类**不是启动配置**，改完的行为各不相同：

| 目录 | 加载者 | 何时读取 |
|------|--------|---------|
| `bisheng/core/prompts/yaml/*.yaml` | `core/prompts/prompt_loader.py` | 进程启动时全量扫目录载入内存——**改完要重启** |
| `bisheng_langchain/gpts/config/*.yaml` | `bisheng_langchain/gpts/assistant.py` 等按**硬编码路径**打开 | 调用时（每次构造实例）读取 |
| `bisheng_langchain/rag/config/baseline*.yaml` | `bisheng_langchain/rag/bisheng_rag_tool.py` 等 | 同上 |

后两类是 LangChain 扩展包（`bisheng_langchain`）的历史实现，属于**运行期资源文件**：它们不参与 `Settings` 的键校验，写错键名不会阻止启动，只会在使用到那条链路时出错。

## 3. 参数如何生效

### 3.1 后端：四层加载链

```
        ┌──────────────────────────────────────────────┐
第 1 层 │ YAML 文件                                     │  ← 进程启动时读一次
        │ 文件名 = 环境变量 config（默认 config.yaml）    │     （模块级 settings 单例）
        │ 相对 src/backend/bisheng/ 解析                 │
        └───────────────────┬──────────────────────────┘
                            │  文件中可用 !env ${BS_XXX} 引用环境变量
                            │  变量不存在 → ValueError，直接启动失败
                            ▼
        ┌──────────────────────────────────────────────┐
第 1.5  │ 环境变量（仅通过 !env 占位符进入）              │
        │ docker compose 的 environment 段提供 BS_*      │
        │ ⚠️ Settings 继承 BaseModel 而非 BaseSettings：  │
        │    没有「BS_* 自动覆盖同名字段」这回事          │
        └───────────────────┬──────────────────────────┘
                            ▼
        ┌──────────────────────────────────────────────┐
第 2 层 │ MySQL config 表，key = initdb_config           │  ← 首次启动从
        │ 内容 = initdb_config.yaml 的 14 个顶层键        │     initdb_config.yaml
        │ 之后由「系统配置」页 / POST /api/v1/config/save │     写入，之后
        │ 或直接改表来维护                                │     YAML 不再被读
        └───────────────────┬──────────────────────────┘
                            ▼
        ┌──────────────────────────────────────────────┐
第 3 层 │ Redis  config:initdb_config                    │  ← TTL 100 秒
        │ 缓存上面那份 YAML 文本                          │     保存时会主动 DEL
        └──────────────────────────────────────────────┘
```

**逐层要点**（对应代码 `bisheng/core/config/settings.py` + `bisheng/common/services/config_service.py`）：

1. **第 1 层（YAML）**：`config_file = os.getenv("config", "config.yaml")`（`config_service.py:24`）；文件不以 `/` 开头时会拼到 `bisheng/` 包目录下，所以 `config` 只要写文件名。加载结果赋给**模块级单例** `settings`（`config_service.py:328`）——**这就是改 YAML 必须重启进程的根因**：进程内没有任何重载逻辑。
   - `!env ${VAR}` 由自定义 PyYAML constructor 处理；**变量不存在直接抛 `ValueError`**，所以源码运行要么导出全部 `BS_*`（见 `data/backend.env`），要么像本机私有配置那样把值内联写死。
   - 顶层键白名单校验，拼错即 `KeyError`。

2. **第 1.5 层（环境变量）**：**没有通用覆盖机制**。`Settings` 继承 pydantic `BaseModel`，不是 `BaseSettings`，所以**不会**自动把 `BS_MINIO_ENDPOINT` 映射到 `object_storage.minio.endpoint`。环境变量只有两条路能进来：
   - YAML 里的 `!env ${...}` 占位符（docker compose 走这条）；
   - 代码里显式 `os.getenv()`，目前只有这几个：
     `BISHENG_PRO`、`BISHENG_DASHBOARD_PRO`、`BISHENG_CORS_ORIGINS`、`BISHENG_RECORD_HISTORY`、`SKIP_MIGRATIONS`（`src/backend/entrypoint.sh`）、历史遗留的 `bisheng_DATABASE_URL`。
   > 反例见 §7.1：`BS_SSO_SYNC__GATEWAY_HMAC_SECRET` 名字看起来像覆盖机制，实际不生效。

3. **第 2 层（MySQL）**：`ConfigService.init_config()` 在首次启动时把 `initdb_config.yaml` 整体写入 `config` 表（key=`initdb_config`）——**仅当表里还没有这条记录**。`merge_old_config` 的合并规则是：以 YAML 的顶层键为准，**DB 已有的键保留 DB 值，DB 没有的键才取 YAML**。所以：
   - 想改这 14 个键 → 改 DB（管理端「系统配置」页），**改 `initdb_config.yaml` 是静默无效的**；
   - 想加一个新键 → 在 `initdb_config.yaml` 里加顶层键，**已存在的部署需要手工把这段补进 DB**（或用管理端页面编辑）；
   - 密码策略、登录方式、工作流上限、灵思预算、MCP 开关、知识库解析器等都在这一层。

4. **第 3 层（Redis）**：读路径是 `get_all_config()` → 先查 Redis `config:initdb_config`，未命中则读 MySQL 并**以 100 秒 TTL 写回**。因此改 DB 后最长 100 秒生效；`POST /api/v1/config/save` 保存时会主动 `DEL` 这个键，所以**从管理端页面改是立即生效的**。

**哪些键走 DB（即在 YAML 里写、但运行时从 DB 读）**——`ConfigService` 的 getter 就是权威清单：

| DB 块名 | 读取方法 | 内容举例 |
|---------|---------|---------|
| `knowledges` | `get_knowledge()` | 文档解析器 `loader_provider`、各 OCR 服务地址、版本管理开关 |
| `workflow` | `get_workflow_conf()` | `max_steps`、`timeout` |
| `password_conf` | `aget_password_conf()` | 密码有效期、登录错误窗口/次数 |
| `system_login_method` | `get_system_login_method()` | `allow_multi_login`、`gateway_login` |
| `daily_chat` | `aget_daily_chat_conf()` | `agent_max_iterations`、`history_max_tokens` |
| `linsight` | `get_linsight_conf()` | 灵思步骤/轮次预算、重试次数（**注意与 YAML 顶层 `linsight_conf` 同名不同层**） |
| `information_conf` | `aget_intelligence_center_conf()` | 情报订阅服务地址与 key |
| `mcp` | `get_mcp_conf()` | `enable_stdio` |
| `shougang` | `aget_shougang_conf()` | 首钢定制开关 |
| `in_app_message_forwarding.cofco` | `get_cofco_forwarding_conf()` | 中粮 E+ 转发（注释里明确写了可热更新） |
| `env` | `get_from_db("env")` | `office_url`、`enable_registration`、上传大小限制 |
| `dialog_tips` | `get_from_db("dialog_tips")` | 会话窗底部提示文案 |
| `default_llm` / `linsight_invitation_code` | `get_default_llm()` 等 | 历史遗留键 |

**反向问题：哪些键只在 YAML？** 连接类与进程级参数都只在 YAML，因为它们必须在**连上 DB 之前**就可用：`database_url`、`database_pool`、`redis_url`、`celery_redis_url`、`openfga`、`sso_sync`、`vector_stores`、`object_storage`、`logger_conf`、`celery_task`、`knowledge_file_worker`、`environment`、`open_api`。

### 3.2 后端：改完要不要重启？

| 你改的东西 | 生效方式 | 要不要重启 |
|-----------|---------|-----------|
| 任意 `*.yaml` 连接/进程级参数（DB、Redis、Milvus、MinIO、日志、pool） | 进程启动时读取 | **要**：重启对应进程（uvicorn / 每个 celery worker / linsight worker 各自都有一份） |
| `initdb_config.yaml` | 仅首次建库时写入 DB | **改了没用**（除非是全新库）；改 DB 才有效 |
| DB 里的 14 个配置块（管理端「系统配置」页保存） | 保存时 `DEL` Redis 键 | **不用**，立即生效 |
| DB 配置被别的途径改动（直接改表） | Redis 100s TTL 过期 | **不用**，最多等 100s；急的话 `redis-cli DEL config:initdb_config` |
| `entrypoint.sh` / 启动命令（并发数、队列） | 进程启动时读取 | **要**，重启 worker |
| compose 的 `environment` / `volumes` / `ports` | 容器创建时生效 | **要** `up -d` 重建（`restart` 不够） |
| 前端 `.env.*` | 见 §3.4 | 视变量性质 |

### 3.3 后端的 `/api/v1/env`：前端看到的派生配置

前端不直接读后端 YAML/DB，它调 `GET /api/v1/env`（`bisheng/api/v1/endpoints.py::get_env`）。这个接口**动态拼装**：

```
environment（YAML） + uns_support（按 loader_provider 是否有 url 动态算）
  + DB 的 office_url / dialog_tips / env 块
  + pro 标志（读环境变量 BISHENG_PRO / BISHENG_DASHBOARD_PRO）
  + version / multi_tenant_enabled / knowledges.version_management
```

所以「前端上传列表里没有 png」这类问题，根因可能在 DB 的 `knowledges.url` 是否配置，而不是前端。另注意 `/api/v1/env` 的 `version` 字段是**源码里硬编码**的（见根 `AGENTS.md` §7），不可信。

### 3.4 前端：构建期 vs 运行期

```
.env.development / .env.production（或 platform/.env.development.local）
        │
        ├── loadEnv(mode, <envDir>, "")        ← envDir 两个 app 不同（§2.3）
        │
        ├─→ vite.config.ts / .mts 读取：          【运行期】dev server / preview 启动时
        │      VITE_PROXY_TARGET、VITE_MINIO_PROXY_TARGET、
        │      VITE_WORKSPACE_PROXY_TARGET、VITE_PLATFORM_ORIGIN …
        │      → 决定 dev server 与 preview 的 proxy 规则
        │      → 改完重启 dev server / preview 即可
        │
        └─→ import.meta.env.VITE_XXX（业务代码里）  【构建期】烘进 bundle
               → 必须重新 build（pnpm build:client / build:platform）
```

关键区别：**同一个变量名，如果它同时被 vite.config 和业务代码读，两处的生效时机不同**。本仓库真实分布是：

- **运行期（vite.config 读）**：`VITE_*_PROXY_TARGET`、`VITE_PROXY_TARGET`、`VITE_WORKSPACE_PROXY_TARGET` —— 决定 dev server / preview 的 proxy，改完重启服务即可。
- **构建期（业务代码读）**：client 通过 vite `define` 把 `VITE_PLATFORM_ORIGIN` 等注入为全局 `__APP_ENV__`（业务代码里写 `__APP_ENV__.BASE_URL`），另有 `import.meta.env.VITE_ENABLE_LOGGER` / `VITE_LOGGER_FILTER` 这类日志开关。**这些改了必须重新 build**。

判断方法：

```bash
grep -rn "import.meta.env.VITE_\|__APP_ENV__" src/frontend/*/src src/frontend/*/vite.config.*
```

### 3.5 通用方法论：三问定位一个参数

面对任何参数，按顺序问三个问题，基本不需要猜：

1. **它在哪个文件里被读到？**
   ```bash
   grep -rn "参数名" --include=*.py --include=*.ts --include=*.tsx --include=*.yml src/ docker/
   ```
   命中 `config_service.py` 的某个 getter → 这是 **DB 参数**（§3.1 第 2 层）。

2. **它是不是顶层键？** 在 `src/backend/bisheng/core/config/settings.py` 的 `class Settings` 里搜字段名——不在里面就是拼错了，启动会 `KeyError`。

3. **改完之后，读它的那个进程重启了吗？**
   - YAML → 重启进程
   - DB → 等 100s 或保存（会主动清缓存）
   - compose → `up -d` 重建容器
   - 前端 → 分构建期/运行期（§3.4）

**打印「实际生效值」的三种办法**：

```bash
# (a) 看 YAML 层解析结果（含 Fernet 解密后的明文密码 —— 注意别贴到聊天窗口/工单）
cd src/backend && PYTHONPATH=. config=config.celery-private.yaml .venv/bin/python -c "
from bisheng.common.services.config_service import settings
print(settings.database_url)
print(settings.model_dump()['object_storage']['minio'])
"

# (b) 看 DB 层原文（需要 admin 身份）
curl -s -H "Authorization: Bearer <token>" http://127.0.0.1:7860/api/v1/config

# (c) 看前端可见的合并结果
curl -s http://127.0.0.1:7860/api/v1/env | jq .
```

## 4. 跨文件耦合清单（改一个要同步改哪里）

这是本仓库最容易「改一半」的部分。以下每一组都是**必须同时改**的：

| # | 约束 | 涉及文件 | 违反的症状 |
|---|------|---------|-----------|
| 1 | MinIO 预签名 Host | 后端 `object_storage.minio.sharepoint` ↔ 前端 `VITE_MINIO_PROXY_TARGET` / `VITE_DEV_MINIO_TARGET` ↔ （容器内）compose 的 `BS_MINIO_SHAREPOINT` | 文件/图片全部 403 `SignatureDoesNotMatch` |
| 2 | MySQL root 密码 | `docker-compose.yml` 的 `MYSQL_ROOT_PASSWORD` ↔ 后端 `database_url` 的 **Fernet 密文** ↔ OpenFGA 的 `OPENFGA_DATASTORE_URI` | 后端起不来 / OpenFGA 迁移失败 |
| 3 | 任何带密码的连接串 | YAML 里必须是 Fernet 密文（`Settings.set_database_url` 加载时**无条件** `decrypt_token()`） | 明文 → 启动抛 `InvalidToken` |
| 4 | 中间件地址的主机名 | 容器内用**服务名**（`mysql` / `redis` / `minio` / `milvus` / `openfga` / `elasticsearch`）；源码运行用 `127.0.0.1:<映射端口>` | 源码运行连不上 / 容器内 DNS 解析失败 |
| 5 | 端口映射 | `docker-compose.yml` 的 `ports` ↔ `docker-compose.override.yml` 的 `ports` ↔ 源码运行的 YAML ↔ `data/backend.env` 的 `BS_*` ↔ 前端 `.env.*` 的 proxy target | 端口冲突 / 连到别的项目的容器 |
| 6 | Celery 队列并发 | `knowledge_file_worker.fair_scheduler.queue_concurrency.<q>` ↔ worker 启动命令的 `-c` **之和** ↔ `celery_task.task_routers` | 任务积压或 worker 空转（注释里写明这是「唯一的硬上限」） |
| 7 | 队列命名 | `ocr_queue_enabled=true` 时必须另外起 `-Q ocr_celery` 的 worker，否则 OCR 任务永久积压 | 知识库 OCR 文件一直「解析中」 |
| 8 | 双前端 origin | `VITE_PLATFORM_ORIGIN`（client→平台）/ `VITE_WORKSPACE_ORIGIN`（平台→client）↔ 实际部署端口 | 跳转 404 / 跳到 IP 而非域名 |
| 9 | 日志落盘路径 | 容器 `/app/data/*.log` ↔ 源码运行相对路径或绝对路径 ↔ compose 的 `./data/bisheng:/app/data` 挂载 | 日志丢失或写到容器内不可见处 |
| 10 | OpenFGA 的 compose 健康检查 | openfga 官方镜像是 distroless（无 shell），**不能写 HEALTHCHECK**，依赖方只能用 `condition: service_started` | 服务永久 `unhealthy`、依赖卡死 |

## 5. 参数没生效的排查决策树

```
改了参数但行为没变
│
├─ 1. 你改的文件，是被运行中的那个进程读的吗？
│     · 容器跑的？→ 挂载的是 docker/bisheng/config/config.yaml
│     · 源码跑的？→ 看启动命令里的 config= 是哪个（本机默认 config.celery-private.yaml）
│     · 前端？→ 看是 client（envDir=src/frontend/）还是 platform（自己的目录）
│
├─ 2. 这个键是从 YAML 读还是从 DB 读？
│     grep 该键 → 落在 config_service.py 的 get_* → 是 DB
│     → 改 YAML 无效，去管理端「系统配置」页改
│
├─ 3. 读它的进程重启了吗？（YAML 只在启动时加载一次）
│     · uvicorn 无 --reload；celery worker 不热加载；linsight worker 也不热加载
│     → bisheng-dev.sh restart <组件>
│
├─ 4. 是 DB 参数但还没生效？
│     100s TTL 未过期 → redis-cli DEL config:initdb_config
│
├─ 5. 是前端变量但构建期读取？
│     grep -rn "<名\|import.meta.env.VITE_\|__APP_ENV__" src/frontend/*/src
│     有命中 → 必须重新 build；只有 vite.config 读的才重启服务即可
│
├─ 6. 是 compose 参数？
│     environment/ports/volumes 变了 → docker compose up -d（restart 不重建容器）
│     改了 override 却用 -f 启动 → override 根本没被加载（§2.1）
│
├─ 7. 顶层键写对了吗？
│     不在 Settings.model_fields 里 → KeyError（启动即失败，不会静默忽略）
│
└─ 8. 还是不对？看进程日志的实际加载行：
      YAML 层每次都会打 debug：Loading <key> from <绝对路径>
      → 直接确认「进程到底读了哪个文件」
```

## 6. 本开发机的实际状态

本机是**混合模式**：前端 + 后端 + worker 全部源码运行，中间件走远端共享栈。

- 启动脚本：`data/bisheng-dev.sh`（`start/stop/restart [-f]/status/logs <组件>`）；组件：`backend knowledge workflow default beat linsight platform client`。
- 后端配置文件：`src/backend/bisheng/config.celery-private.yaml`（由 `data/bisheng-dev.env` 的 `BISHENG_CONFIG` 指定；该文件里的 `BISHENG_RUN_BEAT=0` 表示默认不拉 beat，避免与同事重复触发定时任务）。
- 中间件地址（远端共享栈）：MySQL `172.19.70.107:3306`、Redis `172.19.70.107:6379/{1,2,9}`、Milvus `172.19.70.107:19530`、ES `172.19.70.107:9200`、OpenFGA `172.19.70.107:8080`、MinIO `172.19.70.108:9000`。
- 另一台机器上还有一份 `data/manage.sh`（硬编码 `/root/bisheng/...`，且指向 `127.0.0.1` 的本地 compose 栈）——**在本机用它会连错中间件**，优先用 `bisheng-dev.sh`。
- 本机若要用 compose 起中间件：`cd docker && docker compose -p bisheng up -d`（**不要**用 `deploy.sh`，它会绕过 override，见 §2.1）。
- `BISHENG_RUN_BEAT=0` 与 `linsight_conf.queue_namespace: linsight-local` 是本机私有约定，换机器要重新确认。

## 7. 反直觉点 / 已知坑

### 7.1 `BS_SSO_SYNC__GATEWAY_HMAC_SECRET` 看起来像覆盖机制，实际不生效

`src/backend/bisheng/core/config/sso_sync.py` 的字段说明和 `docker-compose.yml` 的 `environment` 段都在用这个名字，但**没有任何代码读它**：`Settings` 继承 pydantic `BaseModel` 而**不是** `BaseSettings`，不存在「`BS_` + 双下划线分隔的路径」自动映射。真实生效路径只有 YAML 的 `sso_sync.gateway_hmac_secret`。

> 这不是本文的推断——仓库里已有记录：`features/v2.5.1/014-sso-org-realtime-sync/ac-verification.md` 的 D2 项明确标注「env var is **not** picked up… real load path is YAML only」，当时的工作区就是「往 config.yaml 里加 `sso_sync:` 块」。
> **教训：看到形如 `A__B__C` 的环境变量名，不要假定它有效——去 grep 代码。**

### 7.2 `!env` 引用了不存在的变量 → 启动直接失败

不是「值为空」，是 `ValueError: Environment variable XXX not found`。源码运行时若不想导出十个 `BS_*`，就把值内联写进 YAML（本机私有配置就是这么做的）。

### 7.3 顶层键拼错 → 启动直接失败，且报错信息不含文件名

`KeyError: Key xxx not found in settings`。最常撞的是 `linsight`（DB 键名）vs `linsight_conf`（YAML 顶层键名）。

### 7.4 `initdb_config.yaml` 改了没用

它只在**首次建库**时把内容写进 DB；此后 DB 是权威。反向也成立：删除 DB 里 `initdb_config` 那条记录后重启，会用当前 YAML 重新播种——这是重置出厂配置的手段，也会**丢掉所有管理端改过的配置**。

### 7.5 `src/backend/bisheng/config.yaml` 在 `.gitignore` 里，但仍被 git 跟踪

`.gitignore` 第 141 行把它列为忽略，但该文件早就入库了（忽略规则只对未跟踪文件有效）。所以在这台机器上改它**会产生真实的 git diff**，别以为它是本机私有文件。

### 7.6 Compose 列表字段是追加语义

`ports` / `volumes` 在 override 里是**追加**，要替换必须 `!override`。不加的后果是端口「双份发布」——不会报错，只会行为诡异。

### 7.7 DB 配置的 100 秒缓存

改 DB 后别在 100 秒内下结论说「没生效」。管理端页面保存会主动清缓存，手工改表不会。

### 7.8 前端两个 app 的 env 覆盖面不对称

`src/frontend/.env.*` 只服务 client；platform 的开发期覆盖在 `platform/.env.development.local`。开发时「我明明在 .env.development 里加了变量，平台端读不到」是预期行为。

### 7.9 YAML 里的 `environment.uns_support` 是死配置

`config.yaml` / `initdb_config.yaml` 都有一行看起来可配的上传格式白名单：

```yaml
environment:
  uns_support: ['png','jpg', ... 'tiff']
```

但 `GET /api/v1/env` 在拼装响应时**无条件覆盖**这个字段：格式列表来自代码里的静态常量 `UNS_SUPPORT_FORMATS`（含 ofd/wps/dps/et），图片格式则由 `knowledges.loader_provider` 对应的服务是否配了 `url` 动态决定。所以**想让前端支持某种格式，改 YAML 没用**——要去改 `bisheng/api/v1/endpoints.py` 的常量，或把解析器地址配好。

> 这类「YAML 里写了但被覆盖」的项不止一处，验证某个参数是否真的生效，请回到 §3.5 的第 1 步（grep 谁读了它）。
