# 开放 API 密钥鉴权 — 存量调用方迁移指引

> 面向：**平台运维 / 项目交付**（负责切换与回退）与**存量对接方**（负责改造调用方式）
> 依据：F076 开放 API 鉴权（`/api/v2`）——切换与回退口径见规格 ACC「盘点调用方 → 改造 → 预发验证 → 生产切换 → 观察缺失密钥命中」
> 配套：[`docs/api/open-api-auth.md`](api/open-api-auth.md)（密钥用法、权限位、错误码全表）

---

## 0. 一句话背景

`/api/v2` 原先以「默认操作员」（数据库配置 `default_operator.user`）身份执行调用，调用方无需任何凭证。启用本特性后：

- 调用身份 = **密钥所属服务账号的专用身份**（`svc-*`，零角色零资源授权，不继承任何管理员特权）；
- 每个调用必须携带有效密钥，且端点要求的权限位在密钥上（否则 `403/11807`，`data.required` 回带缺哪个）；
- 资源可见范围 = 该身份的**资源授权**（默认空，需要逐项授予）。

**开关默认关闭，关闭时行为与升级前逐字相同**（连无效密钥也不拦）——所以升级本身不影响任何存量对接，切换是显式动作。

## 1. 两个开关

| 层级 | 位置 | 谁能改 | 生效方式 |
|---|---|---|---|
| 部署级（总闸） | 配置项 `open_api.enforce_keys`（默认 `false`） | 运维改配置文件 | **改后需重启后端进程**，无热加载 |
| 租户级 | `PUT /api/v1/open-api/settings`，体 `{"enforce_keys": true}`（缺行 = 未启用） | 超管 / 当前租户管理员 | 写后 ≤5 秒生效（清缓存） |

强制 = **部署级 ∧ 租户级**。两条容易踩的口径：

1. **带密钥的请求只看总闸**：总闸一开，带密钥的调用必然校验、必然按密钥身份执行，租户级开关管不着它。
2. **租户级开关只影响匿名请求**，而且只看**默认租户**那一行：默认租户行开着时，匿名请求 `401/11801`；guest 标记的免登录端点仍按 `default_operator.enable_guest_access` 判定。

## 2. 切换五步

| # | 步骤 | 触发方式 | 要点 | 不做会怎样 |
|---|---|---|---|---|
| 1 | **盘点调用方** | 运维 + 对接方 | 列出所有调 `/api/v2` 的系统：调哪些端点、现依赖哪个身份的权限；确认哪些靠"默认操作员是超管"的短路才能访问资源 | 切换后这些调用按专用身份判定，直接 403/404 |
| 2 | **改造** | 对接方 | 建服务账号 → 按"每个要调的端点"签发带对应权限位的密钥 → 授予所需资源授权 → 调用处改成 `Authorization: Bearer bs-sak-…`（WS 用握手头） | 切换即断 |
| 3 | **预发验证** | 对接方 + 运维 | 在预发打开总闸 + 默认租户开关，跑通全部调用；重点验证权限位齐全（11807）与资源授权（403/404） | 生产切换才发现缺件 |
| 4 | **生产切换** | 运维 | 改 `open_api.enforce_keys: true` → **重启后端** → 打开默认租户开关（`PUT /api/v1/open-api/settings`） | — |
| 5 | **观察缺失密钥命中** | 运维 | 观察 `401/11801` 与 `403/11807` 的出现：前者=还有系统没带密钥，后者=密钥缺权限位；对照第 1 步的盘点清单逐项清零 | 漏改的调用方会静默失败 |

**灰度**：总闸是全平台开关（开或关，无部分生效）；"先小范围"只能通过**先切租户级**实现——但那仅对匿名请求有意义，带密钥的调用一开总闸就强制。因此**上线顺序建议：预发全量验证 → 生产一次性切换**，切换窗口选在调用方改造完成之后。

## 3. 回退

| 场景 | 动作 | 效果与代价 |
|---|---|---|
| **完全回退**（恢复到升级前行为） | 配置 `open_api.enforce_keys: false` + **重启后端** | 全平台、全租户、所有调用（含带密钥的）立刻回到旧行为。**注意需重启，不是秒级**；重启窗口按常规运维流程评估 |
| 只关匿名通道（不重启） | `PUT /api/v1/open-api/settings {"enforce_keys": false}` | 仅影响匿名请求判定；**带密钥的调用不受影响**——对接方不会因此拿回旧身份 |

回退后**保留**的东西：三张表与全部数据（服务账号、密钥、租户策略）、已写入的审计行。**会停**的：逐调用审计（总闸关时无鉴权面，自然无调用审计；管理动作审计不受影响）。

## 4. 排查条目

### 4.1 「切换后存量对接 403/404」——大概率是默认操作员曾配超管

**背景**：早期文档（含本仓 `docs/api/filelib-retrieve.md` 的历史版本）推荐把 `default_operator.user` 配成 `super_admin`"以避免权限边界问题"。切换后身份不再走默认操作员，而是**零授权的专用身份**——原先靠超管短路拿到的资源，现在按授权判定。

**症状**：切换后同一个调用返回 `403/11807`（缺权限位）、`403/11808`（档位不足）或 `404/11809`（不在授权范围）；列表类接口只能看到已授权的资源。

**修法**：给该服务账号**授予资源授权**（管理页「资源授权」，或 `POST /api/v1/service-accounts/{id}/resource-grants:mutate`）。

**不要**把服务账号 owner 换成超管：创建/变更时 `400/11810` 拒绝；万一事后被提权，运行期 `403/11816` 拒绝该账号全部调用（双重防提权，刻意如此）。

### 4.2 「我开了租户开关，为什么没生效」

强制 = 部署级 ∧ 租户级。租户开关的响应里 `deployment_enforced` 会回显总闸状态：它为 `false` 时，租户级开得再高也不生效（`effective: false`）。

### 4.3 「为什么改了配置没反应」

总闸是进程启动时读入的普通配置对象，**没有热加载**：改文件后必须重启。租户级开关才是 ≤5 秒生效。

### 4.4 「切换后没有调用审计了」/「审计里查不到调用」

- 总闸关 → 没有鉴权面 → 不产生调用审计（管理动作审计不受影响）。
- 审计**不在**平台「审计日志」页展示（取证数据），按 `auditlog.action = 'open_api.call'` 直接查库。
- 凭据本身无效的尝试（`401/11801/11802`）**不写审计**（没有可归因身份）；已过凭据校验才失败的调用**会**写。

## 5. 责任与边界

- 本特性交付**能力与迁移指引**；**存量调用方的改造由对接方自行组织**（规格明确不在本特性范围内）。
- 对接方的调用契约见 [`docs/api/open-api-auth.md`](api/open-api-auth.md)；单接口参考见 [`docs/api/filelib-retrieve.md`](api/filelib-retrieve.md) 与 [`docs/api/知识库接口文档.md`](api/知识库接口文档.md)。
- 商业版网关部署（如启用）不代理 `/api/v2` 的 WebSocket 端点，且内容安全/限流发生在后端鉴权之前——两套拓扑的鉴权落点一致，但前置副作用需在设计联调时确认。
